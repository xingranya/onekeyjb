## 7. 踩过的坑（下午别再踩）

1. `setresuid(同 uid)` 会提前 return，不分配 cred；要用 `capset()`。
2. **`execve` 会把 fsuid 重置回 euid**（实测 0 → 2000）。所有需要 fsuid=0 的动作必须在同一进程内完成。
3. `slide_now.py` 的 `selinux_state` 曾硬编码小米地址（差 0x61000），已改成从 VMLINUX 动态查。
4. `kprobe_events`/`dynamic_events`/`uprobe_events` 都是 `0640 root:readtracefs`，组只有读权限，
   permissive 也救不了；只有 fsuid=0 才写得进去。
5. `tracing_on` 默认是 0，建完探针要手动 `echo 1`。
6. 探针名重复会返回 `-17 (EEXIST)`，不影响使用。
7. `finit_module` 用 `allow_shell=1`，否则 shell 不在允许列表里。

## 8. 风险与善后

- 模块已进内核，**重启即消失**（LKM 模式不持久）。
- 两个 `perf_cred` 进程还活着（fsuid=0），重启也会消失。
- 没有写任何分区、没动 bootloader、没改 `/data` 里的用户数据。
- 若设备异常：长按电源键 10–15 秒强制重启即可。

## 9. 关于 SukiSU Ultra 的 LKM 来源（2026-10-19 13:10 补）

用户问「是不是修补 init_boot 给你」。**不是**。

- `init_boot` 是 ramdisk，属于 Magisk 路线；KernelSU/SukiSU 的 GKI 模式修的是 `boot`（内核）。
- 更重要的是：刷任何镜像都要解 BL 锁，本机 `flash.locked=1`，解锁会清数据 ⇒ 这条路直接排除。
- 我们只需要 **`.ko` 文件**（LKM 模式），不需要镜像。

拆了 `SukiSU_v4.2.1_40994-release.apk`（16.4MB）确认：

| 内容 | 说明 |
|---|---|
| `lib/arm64-v8a/libksud.so` (5.5MB) | 用户态 ksud（可直接当可执行文件用） |
| `lib/arm64-v8a/libkernelsu.so` (14KB) | 管理器 JNI，不是内核模块 |
| `assets/kpimg` / `kptools` | KernelPatch 镜像与工具（另一条路线） |
| 内嵌 AArch64 ET_REL | 只有 `.text.ksu_bootstrap`（bootstrap），**不是 kernelsu.ko** |

GitHub release 资产也只有 APK（`api.github.com` 确认），没有 `.ko`。
⇒ SukiSU 的 LKM 是管理器运行时按 KMI 获取/构建的，APK 里抠不出来。

### 可行顺序

1. 先用**已经载入的 KernelSU-Next** 拿 root：`ksud` 同样能从 APK 的 `libksud.so` 取，
   或直接用仓库里的 `ksu/ksud.arm64`。
2. 有 root 之后，再让 SukiSU 管理器下载/生成它自己的 `android17-6.18_kernelsu.ko`，
   或从管理器缓存里直接抓。
3. 两个 fork 模块名都叫 `kernelsu`，不能共存；换 SukiSU 需要重启后重走一遍 UAF 链加载。

### 10.1 做了什么

- `ksud 3.3.1` 与模块 3.4.2 不匹配 → 换官方 **ksud 3.4.2**
  （`KernelSU-Next` release 的 `ksud-aarch64-linux-android`）。

- 改为让 `perf_cred` 在 **fsuid=0 的窗口里自己铺目录**：
  `mkdir /data/adb{,/ksu,/ksu/bin,/modules}` → 拷贝 `ksud342` → `chmod 755`
  → `symlink /data/adb/ksu/bin/su -> /data/adb/ksud`。
  实测 `copied=7059592`、`LAYOUT_DONE`。
- 关键坑：**`execve` 会把 fsuid 重置回 euid**，所以铺目录必须在同一进程内用
  `mkdirat/openat/write` 完成，不能 exec 到 shell。

### 10.2 su 为什么还是不行

- `/system/bin/su` 被模块伪造成 ksud（dmesg：`newfstatat su->ksud!`、`faccessat su->ksud!`），
  但 **execve 没有被重定向** → `su: can't execute: Permission denied (126)`。
- `ksud342 feature list`：所有特性都是 `[NOT_SUPPORTED]`；
  `feature get su_compat` → `ksuctl failed: Operation not permitted`。
- 说明 `su_compat` 没开，且 shell 不在允许列表里 → **`allow_shell=1` 很可能没生效**。
- `/sys/module/kernelsu` 不存在（模块把自己的 sysfs 藏了或内核侧没建），
  所以也无法从 sysfs 读参数确认。
- 模块读不到 `/data/system/packages.list`（dmesg：`track_throne: open ... failed: -13`），
  管理器无法被加冕，也就没人能开 `su_compat`。
- 想 chmod packages.list 需要 `CAP_FOWNER`，而 fsuid=0 不够（文件属主是 system）。
