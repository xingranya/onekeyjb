# 版权与来源声明（合并版 v2.4）

> 用途：面向群友/README/Release 的正式说明；同时回答“我的项目算不算抄他的”。
> 结论先行：**在合并前，你的 v2.1–v2.3.3 与 Yunnijian 的仓库是两套独立实现，不构成抄袭；v2.4 合并了他仓库里的少量资产/思路，因此 v2.4 必须署名并保留他的 MIT 许可声明。**

## 一、事实（有据可查）

1. 两边没有 git 关系：GitHub API 显示上游 `fork=false`，上游是 6 个独立 commit（2026-10-20 13:56～18:22），本地是 v2.1 之后未提交的 v2.3.3 工作树。
2. 两边共用的是**公开 CVE 工具链**：`third_party/` 与公开仓库 `Feng1586/CVE-2026-64560-public`（Apache-2.0）逐字节一致；KernelSU / KernelSU-Next / SukiSU / BakaSU / Stellar / COUI 均为各自上游开源项目。
3. 上游真正新增的功能只有两条：**反 root 守卫**（`com.oplus.exsystemservice` disable→kill→5s→enable）与 **4 管理器选择**；其余是它自己的重写（Kotlin/Compose/Shizuku/自编 LKM/设备端 C 工具）。
4. 上游在它的 README 与 `NOTICE` 中列出了第三方组件（公开 CVE 工具链、KernelSU、KernelSU-Next、BakaSU、SukiSU、Miuix、Shizuku），**但没有提到你的项目**——因为它并没有复制你的代码，是独立实现。
5. 你在 v2.1–v2.3.3 的工作（Stellar 通道、管理器校验、Live 等待、su 自检、原子投放、Java UI、root 修复流程、测试）与上游代码没有对应关系；合并前的版本不构成对其代码的抄袭。
6. **v2.4 合并了什么**：上游的 `run.sh` 六步流程思路、4 管理器资产（4 个 ko + ksud）、反 root 守卫逻辑；“默认 su 不建挂载”的路线；此外源码层新写了 Stellar 通道、COUI UI、检查/清理逻辑。按上游 MIT 许可，合并其资产/脚本必须保留版权与许可声明。

## 三、“算不算抄”的结论

- **合并前**：不算。两套独立实现，共用公开工具链与开源库；功能点/思路本身不受著作权保护，代码表达不同。
- **合并后**：不能说“完全原创/与上游无关”。v2.4 使用了上游的 MIT 代码/资产（run.sh 结构、LKM、ksud、exploit 资产），**必须署名并保留 MIT 许可**；但也不等于“抄袭”——MIT 明确允许复制、修改、再分发，只要保留版权声明。
- **反向也不成立**：没有证据表明上游复制了你的代码；两边同一天各自开发，方向不同。
