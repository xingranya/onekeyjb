# 160 · 一加 16（PYB110）CVE-2026-64560 实测确认：漏洞存在

日期：2026-10-19
设备：OnePlus 16 / `PYB110` / ColorOS `PYB110_17.0.0.155(CN01)` / SM8975
内核：`6.18.21-android17-5-gf957accaf563-ab15926176-4k`（构建于 2026-07-23）
补丁级：2026-10-01

## 0. 结论

**漏洞存在，已实测命中。** 用仓库里不依赖任何内核地址的 v33 oracle，
在第 6 次 attempt 拿到内核回写指针，低 12 位与页内偏移自洽：

```
LEAK attempt=6 fd_idx=1509 off=0x1160 val=0xffffff88832df160
LEAK_TOTAL attempt=6 n=1
```

`0xffffff88832df160 & 0xfff == 0x160`，与 `off=0x1160` 一致 —— 即
`timerqueue_del()` 末尾 `RB_CLEAR_NODE()` 把悬空节点自身地址写回了我们喷的 8KB frag 页。

**但小米那套完整链路不能直接搬。** 前半段（零特权 UAF + 页级重占）完全可复用，
后半段有 4 个断点，见 §4。

## 3. 实测过程

### 3.1 冒烟

```
./t64560_v33 0 400 16 6000 20000
v33 attempts=0 ... baseline=487/609
```

二进制为 aarch64 静态链接，在 `u:r:shell:s0` 下可直接执行，`/proc/slabinfo` 可读。

### 3.2 第一轮：40 次，零命中

```
attempt=1..40 drained=2(8s) leaks=0   DONE attempts=40
```

排空门几乎全部走宽松门（`drained=2`），严格门只过了 1 次。
按小米实测 2.9%/attempt，40 次零命中的概率约 31%，**属统计波动，不足以否定**。

### 3.3 第二轮：第 6 次命中

干净 boot 后严格门稳定通过（`drained=1`，5.1s 左右）：

```
attempt=1..5 drained=1 leaks=0
LEAK attempt=6 fd_idx=1509 off=0x1160 val=0xffffff88832df160
LEAK_TOTAL attempt=6 n=1
attempt=7..17 leaks=0
<第 17 次后内核 panic，设备自动重启>
```

### 3.4 崩溃说明

第 17 次之后 adb 掉线，设备自动重启（`bootreason=reboot`，uptime 归零，无线调试换端口回来）。
这与 README §7 描述一致：**命中但那一页不是我们的**时，`rb_erase` 会作用在已被复用的
`k_itimer` 上，导致内核 panic。属该链固有风险，不是设备损坏。

## 4. 后半段的 4 个断点

| # | 断点 | 小米 | 一加 | 影响 |
|---|---|---|---|---|
| 1 | `kprobe_events` 可写 | 可 | **不可**（0600 root，SELinux getattr 都拒） | 原链第 4–5 步「任意读 + 拿 cred 地址」整段失效 |
| 2 | `dmesg` / `logcat -b kernel` | 可 | **不可** | 命中/崩溃观测要靠设备重启 + 日志文件 |
| 3 | `kallsyms` / BTF | 可读符号名 | **全封** | 没有符号与结构偏移，`selinux_state` 地址算不出 |
| 4 | `MODULE_SIG_PROTECT` | 无 | **有**（`protected_module_names_list`） | 未签名 ko 能否 `finit_module` 未知 |

补充：`available_filter_functions` 不存在（`CONFIG_FUNCTION_TRACER` / `DYNAMIC_FTRACE` 未开），
所以连函数名列表都拿不到；但 `events/sched/sched_blocked_reason/enable` 可写，
`trace` 可读，**ftrace 的 `%pS` 通道仍然可用**。

## 5. 下一步

1. **必须拿到 PYB110 的 boot.img**（全量包解 `payload.bin`，或社区 dump）。
   有了 vmlinux 才能：恢复符号 → 算 `selinux_state` → 重打 `kernelsu.ko` 的 vermagic/符号。
2. 反汇编四个修复标记（`timer_lock_sighand` 是否存在、`posix_cpu_timer_del` NULL 分支是否重试、
   `__lock_task_sighand` 是否有 acquire 屏障、`release_task` 是否 `stlr`），做静态交叉验证。
3. kprobe 替代方案：`perf_event_paranoid=-1`，待验证能否通过 perf kprobe PMU 建探针。
4. `MODULE_SIG_PROTECT` 语义待验（保护名单是「仅列名强制签名」还是「除白名单外全强制」）。

## 6. 复现命令

```bash

adb -s $D push bin/t64560_v33 /data/local/tmp/
```

## 7. 后续进展（2026-10-19 下午）

### 7.1 静态确认（boot.img 已拿到）

`一加_16_17.0.0.155_boot.img` → 裸 ARM64 Image（43MB，未压缩）
→ `vmlinux-to-elf` 恢复 **143,444 个符号**，链接基址 `0xffffffc080000000`。
四个修复标记与小米机逐条一致，**全部指向未修**（见 §0 表格）。

关键地址：
- `selinux_state` = `0xffffffc082979630`（`.bss`），`avc_latest_notif_update.notif_lock` 在其 -8
- `sig_enforce` = `0xffffffc08294f208`（MODULE_SIG_PROTECT 的实际开关，可清零）
- `current->cred` 在 task+0x908；`cred->fsuid` +0x20；`cred->cap_effective` +0x40

### 7.2 KASLR slide

`grab.sh` + `slide_now.py` 6 组锚点一致：**slide = 0x1be9200000**，
`_text = 0xffffffdc69200000`，`selinux_state = 0xffffffdc6bb79630`。

**踩坑**：`slide_now.py` 里 `SELINUX_STATE_LINK` 硬编码的是小米地址 `0xffffffc082918630`，
与本机差 `0x61000`，第一次写把 8 个零打到了 `__kvm_nvhe_*` 数据区（无害）。
已改为从 VMLINUX 符号表动态查。

### 7.3 SELinux → Permissive（成功）

`t64560_v36 0 0xffffffdc6bb79629 80 400 16 6000 12000 4500`，第 45 次落地：
`getenforce = Permissive`、`enforce=0`、`policyvers=35`（initialized 保留）、`id` 仍是 `u:r:shell:s0`。
副作用：**dmesg 变得可读**（此前是 SELinux 拦的）。

### 7.4 绕过 kprobe 限制：perf tracepoint 泄漏 cred

一加的 `kprobe_events`/`dynamic_events`/`uprobe_events` 全是 `0640 root:readtracefs`，
组只有读权限 ⇒ DAC 挡住，permissive 无效。

替代路径：`perf_event_paranoid = -1` ⇒ `perf_paranoid_tracepoint_raw()` 放行，
`perf_event_open(PERF_TYPE_TRACEPOINT)` 不受 tracefs 文件权限约束，
且 `PERF_SAMPLE_RAW` 里是**未哈希裸指针**。

`src/perf/perf_cred.c`（aarch64 freestanding，clang + lld 交叉编译）实测：
```
tracepoint id=314
perf fd ok
ioctl=0
capset=0
read=8 count=1
HIT pid=31411 tid=31411 ptr=0xffffff88e36b7f00 site=0xffffffdc6934f140
```
`site - slide = 0xffffffc08014f140 = prepare_creds + 0x2c` ⇒ 拿到的就是 `capset()` 新 commit 的 cred。

**注意**：`setresuid(同 uid)` 会提前 return，不分配 cred（实测 count=0）；必须用 `capset()`。

### 7.5 下一步

1. UAF 零写 `cred+0x20`（fsuid/fsgid）→ 该进程可写 `kprobe_events`（0640 owner rw）。
2. `perf_cred` 自检到可写后 exec `stage2.sh` → 建 kprobe，拿任意内核读。
3. 写 `cap_effective = cred+0x40`（地址值写入）→ 拿到 CAP_SYS_MODULE。
4. 清零 `sig_enforce` + 重打 `kernelsu.ko` vermagic/符号 → `finit_module` → ksud install。
