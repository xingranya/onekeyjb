# 155 — 64560 落地 oracle 实测成功 · 第六条（task/cred 地址）的真实卡点

> 2026-10-18 02:57

## 1. 结论摘要

- **新能力到手**：`t64560_v30` 在实机上打出了 **`ORACLE_HIT`** —— 内核把一个真实 `k_itimer`
  地址写进我们控制的 8KB 页，**victim 存活、设备未重启**。这是第一次有"不退出、不崩溃"的落地判据。
- **第六条仍未达成**：`collect_posix_cputimers` 的 `current → node+0x48` 这条路被 `cpu_timer.head`
  （`node+0x20`）卡住 —— 该字段必须是真实的 `&sig->cputimer.timers`，否则节点不被摘除，
  同一节点被重复处理，第二次 `list_add` 触发 `list_add double add` → panic。
- 因此现在的瓶颈从"能不能落地"变成了**"能不能拿到 `signal_struct` 的地址"**。

## 2. oracle 实测证据

```
ORACLE_HIT attempt=23 fd_idx=180 off=0x1468 val=0xffffff88a99b12e0
ORACLE_HIT attempt=23 fd_idx=659  off=0xce8  val=0xffffff88a99b0560
ORACLE_TOTAL attempt=23 n=2
```

`0xce8 = 0x180×8 + 0xe0 + 0x08` → 正好是第 8 个槽位的伪造节点 `rb_right`。

机制：喷雾之后向 victim 的 cputimer 树**插入**一个 3600s 远期计时器，`timerqueue_add` 的
`rb_link_node(&new->node, parent, link)` 把 `new`（真实 `k_itimer`）写进 `parent->rb_right`；
`parent` 就是我们的伪造节点。伪造节点设为 `__rb_parent_color=1`（parent=NULL + BLACK），
插入时 `rb_is_black(parent)` 立即 break，不去解引用 `gparent` ⇒ 安全。

**副产品**：`val` 是一个真实的 `posix_timers_cache` 对象地址，可用作该 cache 的页级标定。

## 3. 为什么 collect 现在还不能用（反汇编证据）

```
0x213e30  ldr  x8, [x22,#0x18]        ; node->expires
0x213e38  cmp  x23, x8 ; b.lo ...     ; samples < expires → 跳过
0x213e40  strb w25(=1), [x22,#0x40]   ; firing = 1
0x213e44  mrs  x8, sp_el0             ; current
0x213e4c  stlr x8, [x22,#0x48]        ; ★ task = current（目标）
0x213e50  ldr  x0, [x22,#0x20]        ; head
0x213e54  cbz  x0, 0x213e64           ; head==0 → 跳过 timerqueue_del ★
0x213e58  mov  x1, x22
0x213e5c  bl   timerqueue_del
0x213e60  str  xzr, [x22,#0x20]
0x213e64  add  x0, x22, #0x30         ; elist
0x213e68  ldr  x1, [x20,#8]           ; firing->next
0x213e94  ldr  x22, [x19,#0x10]       ; 下一个节点（真 head 的 leftmost 缓存）
0x213e9c  cbnz x22, 0x213e30          ; 还有就继续
```

`node+0x20` 是 `struct cpu_timer.head`。`head==0` ⇒ 不摘节点 ⇒ `timerqueue_getnext`
（返回**真 head 缓存的 `rb_leftmost`**）仍然是我们这个节点 ⇒ 第二轮 `list_add`
（`elist` 已挂在 `firing` 上）走 `__list_add_valid_or_report` ⇒ **double add → BUG/panic**。

`cpu_timer.head` 只在 `posix_cpu_timer_set` 里对**真实计时器**赋值为 `&base->timers`，
我们的伪造对象永远不会被内核写入这个字段 ⇒ 必须自己填，而它位于 `signal_struct` 内部。

**安全的一面**：`posixtimer_send_sigqueue` 开头 `pid_task(tmr->it.cpu.pid, ...)`，
返回 NULL 时跳到 `0xffffffc08010ed48` → `__rcu_read_unlock` + `ret`，**干净返回**。
所以只要 `node+0x28`（`cpu_timer.pid`）是 0，发送侧不会崩。

## 4. 为绕开 head 做过的尝试（都排除了）

| 尝试 | 结果 |
|---|---|
| 伪造 `head` 指向页内假 `timerqueue_head` | 真 head 的 `rb_leftmost` 缓存不会更新 ⇒ 仍重复 ⇒ 仍 panic |
| 让我们的节点不是 leftmost（expires 设大） | 节点就永远不会被处理，拿不到 `current` |
| 全内核静态扫"`current` 写入堆对象"的替代点 | `mrs sp_el0` 命中 **42,015** 处、去重后 11,688 种写法，绝大多数是内联 `current` 的普通使用，没有一个"目标对象可由用户态接管"的落点 |
| `/proc/net/unix` 的 `%pK`（root 视角） | `cat: Permission denied`（hypsys 也读不了 `proc_net`） |
| 让 WARN 打印 `Kernel Offset` | WARN 不打印（只有 oops/panic 打印），而 oops 必重启 |

## 5. 第六条的两半，分别缺什么

| | 需要 | 现状 | 缺的东西 |
|---|---|---|---|
| **6a** 拿 task/cred 地址 | 一次"把内核指针写进我们可读页"的路径 | oracle 只能给 `k_itimer` 地址 | `signal_struct` 地址（补 `head`） |
| **6b** 提权 | 有效 `cred`（含 `user_ns`/`security`）或内核镜像地址 | 只有 8 字节零写 | 一个**读**原语，或 KASLR slide |

`cred_jar` 页复用 + 逐 slot 清零 `uid` 只能得到 `uid=0`：`cap_effective` 仍为空、
SELinux 域仍是 `shell` ⇒ **不构成 root，不作为目标**。

## 6. 建议的下一步（按性价比）

1. **`signal_cache` 页复用 → 补 `head`**（当前唯一自洽的路）
   - 复用已有的"已知页"手法：先泄露页 P（oracle/`RB_CLEAR_NODE`）→ 释放 → fork 风暴
     让 `signal_cache` 取到 P → 该 victim 的 `sig` 落在已知页；
   - `&sig->cputimer.bases[i].timers = sig + off`（BTF 可算）⇒ 填进伪造节点 `node+0x20`；
   - 之后 collect 就能正常摘节点 ⇒ 一次拿到 `current`。
   - 风险：需要"两页协同"（`posix_timers_cache` 页 + `signal_cache` 页）同时命中，概率低但可测。
2. **工程化 oracle**（已在做）：`v31` 修掉"探针计时器泄漏导致 slab 漂移"和"基线漂移"，
   `t64560_v31 300 400 16 6000 12000` 已挂机（~8s/attempt，判据 `ORACLE_HIT`）。
3. **备选新面**：内核里 `io_uring` 是编进去的（`io_uring_create`/`io_ring_ctx_alloc`/
   `io_uring_alloc_task_context` 等符号都在），如果 shell 能调 `io_uring_setup`，
   那是一个全新的、历史上多漏洞的表面 —— 值 10 分钟验可用性。
4. **不再投入**：`kmem`/`workqueue` tracepoint（perfetto 只认固定类型）、文件类地址通道
   （kallsyms/modules/iomem/timer_list/printk_formats/vmcoreinfo 全封）、trace 文本指针（`hash-ptr`）。
