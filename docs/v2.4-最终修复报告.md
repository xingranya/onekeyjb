# v2.4 最终修复报告（默认 su 软重启不丢失 + 安装包瘦身）

## 为什么"他做的"软重启后默认 su 不丢，我们的会丢
- 他的工具：默认 su 完全走 **KernelSU 内核侧 su wrapper**（内核 file wrapper），不依赖任何 userspace 挂载。
  软重启只重启 zygote/system_server，内核模块仍在 → su 一直可用。
- 我们之前：本机 shell 域执行 /system/bin/su 会被内核拦（EACCES），为了 PATH su 可用，
  额外加了 userspace overlay（/system_ext/bin），底包放在 **/data/adb/onekey-su（0700 root）**。
  软重启后普通进程无法遍历 /data/adb → overlay 里 su 变成 Permission denied → 看起来"默认 su 丢了"。

## 修复
- 兼容层底包改到 **/data/local/tmp/onekey-su**（所有用户可遍历，755）
- overlay 挂载加 `override_creds=on`
- 每次部署前卸载旧 su_compat 挂载并删除旧 /data/adb/onekey-su
- 状态卡新增"默认 SU：已就绪/未就绪，点修复"提示

## 软重启持久性实测
执行 `setprop ctl.restart zygote`（等价软重启，uptime 不归零）后：
- `su_compat` overlay 仍在
- `/system_ext/bin/su -c "id -u"` = **0**
- 应用「root 诊断」= **4/4 全通过**（uid=0，CapEff=000001ffffffffff，u:r:ksu:s0，私有/存储可读）

## 边界说明
- 软重启（zygote/SystemUI/系统框架重启）：默认 su 保持，不需要重做
- 整机重启：KernelSU 是 late-load 内核模块，重启后模块消失（**两个工具都一样**），
  需要重新点一次「一键越狱」；之后管理器授权过的应用重新打开即可
- 应用按 PATH 调用 su 即 root；若某应用写死 /system/bin/su 且在 shell 里执行仍受内核限制（上游同样如此）

## 4 管理器修复失败的原因与修复（2026-10-21）
现象：SukiSU 修复后 root 诊断 4/4，其余 3 个管理器修复直接报「无法确认当前 root 的配套版本，停止修复」。

原因：修复模式需要先识别当前内核属于哪个管理器。旧逻辑只认 SukiSU(40994) 和 KernelSU-Next(33355) 两个 version 数字，
BakaSU（version 35235，full_version 带 @BakaSU）和 KernelSU 官方（32680）都被判为“未知” → 直接中止。

修复：
1. 新的 detectLoadedSpec 三级识别：
   - full_version 名字匹配（BakaSU/ReSukiSU、SukiSU、Next/KSUN、KernelSU）
   - version 数字匹配（40994 SukiSU / 35235 BakaSU / 33355 Next / 32680 官方）
   - 已安装管理器兜底（只装了一个时直接用）
2. 仍无法识别时不再中止，回退到界面选择的管理器继续修复
3. 修复时把 ksud debug info 全部打进日志，失败可直接定位
4. 4 个管理器统一收尾：ksud install → packages.list 加冕 → manager add/set-enabled → su_compat → su_forward PATH 兼容层 → 重启管理器
5. 版本不匹配只告警不中止（strict 已取消退出）

## 注意
- 切换不同管理器的内核必须重启一次（LKM 是 late-load，不能热切换）
- 管理器版本必须与内核模板匹配：Next 3.4.2 / 官方 3.3.1 / SukiSU v4.2.1 / BakaSU v4.2.0-rc3(35235)
