# OneKeyJB v2.4 合并报告（星苒鸭 × Yunnijian 上游）

> 日期：2026-10-20 ｜ 产物：`merged-app/` + `dist/OneKeyJB-v2.4.0.apk`
> 真机：OnePlus 16 / PYB110，ColorOS 17，当前已安装 v2.4.0（覆盖 v2.3.3，同签名）

## 1. 结论速览

1. **上游 Yunnijian 是独立重写**（独立 6 个 commit，`fork=false`），与 v2.3.3 没有 git 关系，不能 merge/cherry-pick；本次按“功能/资产级移植 + 架构重搭”合并。
2. 上游真正新增的只有两条：**越狱后禁用安全弹窗**（`com.oplus.exsystemservice` disable→kill→5s→enable，规避检测弹窗与 15s 重启）与 **4 管理器选择**（KernelSU / KernelSU-Next / SukiSU Ultra / BakaSU）。其余是换实现。
3. v2.4 保留了他这两条，并补齐我们 v2.3.3 的优点：模块 Live 等待、失败安全中止、Stellar 通道、日志导出、自动跳转运行日志、赞赏弹窗、清理旧兼容挂载。
4. **默认 SU 采用上游思路：不创建任何全局挂载**，依赖管理器原生 sucompat + `allow_shell=1`；v2.3.3 的 `/system_ext/bin/su` + `onekey-su` overlay 降级为默认关闭的“兼容模式”开关，并在越狱时自动清理旧版本残留。
5. UI 用 **COUI 1.1.0** 完全重写（含 coui-blur / 触感），移除 Miuix 与 Material 组件；参考 OPlusKey 的“设置页”布局（大标题顶栏 + SmallTitle 分组 + 卡片列表），保留头像/图标/赞赏弹窗。

## 3. 越狱路径对比：谁的更好？

### 3.1 我们的 v2.3.3 更强的地方
- 管理器版本 + 签名 SHA-256 + UAPI 校验，避免“管理器显示未安装/版本不匹配”类问题；
- `ksud manager add` 显式加冕 + 回读，管理器连接有实证；
- 模块必须 `Live` 才继续，避免 `Loading` 期触发 GRANT_ROOT 导致 kernel panic/重启；
- 唯一 runId、原子投放、长度校验、全命令超时、su 三路自检（绝对路径/stdin/-M）；
- Stellar 通道（ColorOS 17 上 Shizuku 的 ADB 权限受限）；
- 有 4 组单元测试。

### 3.2 上游更强的地方
- **反 root 守卫**：ColorOS 的 `com.oplus.exsystemservice` 会在检测到提权后弹窗并 15s 后 reboot；上游用 disable→kill→5s→enable 规避，这是 v2.3.3 缺失的、实打实减少重启的修复；
- **管理器覆盖更广**：官方 KernelSU 与 BakaSU 两条路线（v2.3.3 只有 KSU-Next / SukiSU）；
- **默认 SU 更干净**：不创建 `/system_ext/bin/su` overlay，普通 App 侧没有额外挂载痕迹；
- 自编 LKM（但见 3.3 的坑）。

### 3.3 上游资产的关键坑（已在本版修复）
- 上游 4 个 ko 里 3 个（Next/BakaSU/SukiSU）`.modinfo` 仍是 `vermagic=6.18.21-4k`，按 `docs/158/162` 在 PYB110 上会 `finit_module` 失败；v2.4 构建期统一重打为 `6.18.21-android17-5-gf957accaf563-ab15926176-4k ...`（已验证 4 份 ko 的 vermagic）；
- 上游 run.sh 无论 su 是否成功都 `echo DONE`、无 Live 等待、无失败中止；v2.4 已加 `LIVE_TIMEOUT` / 失败退出码；
- 上游每次固定投放 40.9MiB 资产、部署目录不清理；v2.4 只投放当前管理器所需 ko/ksud（约 10MiB），工作目录 0700 并可清理；
- 上游用 `chmod 644 /data/system/packages.list` + mv 回环触发加冕，会动系统文件权限；v2.4 保留但仅作为兜底（更推荐 `ksud manager add`）。

### 3.4 结论
- **纯“稳定拿到 root”**：v2.3.3 的校验与安全边界更好；
- **减少 ColorOS 弹窗/重启**：上游的反 root 守卫更好（已合并）；
- **隐藏环境**：上游“不建挂载”的思路更好（已采用）；我们旧的 overlay 确实可被检测（见第 4 节）；
- **v2.4 = 上游的两条真新增 + 我们的严谨链路 + 默认隐藏 + COUI UI**。

## 4. 默认 SU：他到底怎么解决的？我们旧版的问题

### 4.1 上游的做法（v2.4 采用）
- 模块加载时传 `allow_shell=1`（4 个 LKM 都定义了该参数）；
- 依赖 KernelSU 系内核的 **sucompat**：内核按允许列表对目标 uid 伪装 `/system/bin/su`，exec 时把 fd 换成管理器 ksud；
- App 是否能用 su 由**管理器授权列表**决定；上游不在文件系统上创建任何 `su` 文件/overlay；
- `run.sh` 直接 `su -c ...`，没有 `su_path_compat` 之类补偿。

### 4.2 我们 v2.3.3 的做法与问题
- 为了让“搜不到 su 的 App”也能用，v2.3.3 用 `su_path_compat.sh` 在 `/system_ext/bin` 做 **全局 overlay**（source=`onekey-su`，lowerdir=`/data/adb/onekey-su-compat/bin`），放入 `su_forward`；
- 真机取证（`docs/detection-audit.md`，5 个视角）确认：`/proc/self/mountinfo` 对 **任何 App** 都含 `overlay onekey-su /system_ext/bin ...`；普通 App 可 stat/读/执行 `/system_ext/bin/su`（9056B，md5=su_forward），`statfs`=overlay、`mount/df` 显示 `onekey-su`；
- 结论：**这两个东西无法在“全局生效”的同时对检测 App 隐藏**；
- 另外 `/data/local/tmp/onekey` 工作目录 0755/0644，普通 App 可枚举读取 `root_stage.log`、exploit、`manager.apk` 等 28MB 残留（v2.4 已改为 0700 + 清理）。

### 4.3 v2.4 的取舍（带开关）
- **默认**：不创建 `/system_ext/bin/su`、`onekey-su` overlay 或 `/data/adb/onekey-su-compat`；越狱开始/结束时自动清理旧版本残留；
- **兼容开关**：`默认 SU 兼容模式（不推荐）`，默认关闭；只有用户明确打开才执行旧 overlay 兼容，并在 UI 提示“会产生可检测挂载痕迹”；
- **推荐**：授权 App 由管理器负责；如果某个 App 仍找不到 su，先检查管理器授权/重启 App，再考虑打开兼容开关；
- 已加“清理旧兼容挂载”入口（卸载 `source=onekey-su` 的挂载、删除 `/data/adb/onekey-su-compat`、删除旧 `/data/local/tmp/onekey`）。

## 5. 隐藏环境还能做什么（后续）
- 首推 **KernelSU-Next** 路线：sucompat 是内核态伪装，非白名单 App 连 `/system/bin/su` 都看不到（ENOENT）；SukiSU 路线在部分管理器配置下可能出现真实文件/挂载痕迹，建议作为可选项并提示；
- 运行中避免任何 `su -M` 全局挂载；若未来要“默认 su + 隐藏”兼得，正确方向是 **按目标 App 的 mount namespace 注入**（只在该 App 命名空间可见），而不是全局 overlay；
- `/data/local/tmp` 工作目录 0700、跑完清理；不要保留 exploit/日志明文；
- 管理器“直接安装/修补 boot”在临时 root 下必须禁用（会破坏 boot/recovery，已有真实变砖案例）。

## 10. 稳定性对比：为什么群友用“他那个版本”会重启 2–3 次？

### 10.1 上游流程的稳定性风险（已在本版规避/降级）
1. **模块 Loading 期就调用 su/ksud**：上游 run.sh 只 grep kernelsu /proc/modules，没有等待 Live；在 Loading 状态执行 su/GRANT_ROOT 会触发内核竞态（我们 v1.5 已实证会 panic/重启）。v2.4 增加 90s Live 等待 + LIVE_TIMEOUT 安全中止。
2. **chmod/mv /data/system/packages.list 加冕**：上游靠移动系统包管理文件触发 pkg_observer；这会扰动 PackageManager/zygote，是软重启/系统不稳的高风险来源。v2.4 已删除该操作，改为 ksud manager add + set-enabled（失败只提示，不动系统文件）。
3. **4 个 LKM 里 3 个 vermagic 不匹配**：上游资产在 PYB110 上会 finit_module 失败；失败后无中止，用户重复点越狱 → 多次重启。v2.4 构建期已统一重打 4 份 ko 的 vermagic。
4. **没有失败中止/单次尝试约束**：上游不管成败都 echo DONE，失败后用户重试；v2.4 失败返回错误码并停止本次流程，不做自动重试。
5. **权限/检测状态**：上游部分路径留在 Permissive，ColorOS 检测到后 15s reboot；反 root 守卫只覆盖启动窗口。v2.4 保留 Enforcing（按管理器实际状态），守卫加 trap 恢复，避免安全组件长时间被禁用。
6. **模块冲突**：群友日志里 Zygisk Next / LSPosed / mountify 与 KSU 同时存在时，zygote/system_server 崩溃、ksud feature 10003/KPM ioctl 不匹配，会放大重启概率。建议验证时先清空 Zygisk/LSPosed/mountify 等模块，只保留 root。

### 10.2 我们 v2.3.3 一次成功的原因（本版保留其安全思路）
- 只加载本机验证过的 LKM（vermagic/cred/noenforce 已处理），模块必须 Live 才继续；
- fsuid 阶段先把 ksu_cred->fsuid/fsgid 归零，避免管理器/ksud 打不开；
- 用 ksud manager add 显式登记管理器（不动 packages.list）；
- 原子投放、长度校验、全命令超时、失败即退出；
- su 三路自检（绝对路径/stdin/-M），失败不报 DONE。

### 10.3 本版建议
- **稳定性优先**：选 **KernelSU-Next / SukiSU Ultra**（本机已验证链路），官方 KernelSU / BakaSU 先视为实验性（资产已备好，待真机验证）；
- 越狱前**移除 Zygisk Next / LSPosed / mountify** 等内核/注入模块，避免 zygote 崩溃；
- 不要在越狱后点管理器“直接安装/修补 boot”（已有变砖案例）；
- 越狱完成后本版会清理 /data/local/tmp/onekey-*、ksu-official.ko、ksud_official 等临时文件，减少被检测面与磁盘残留。

## 11. 群友日志（verbose 2026-10-20）问题定位与解决

### 11.1 日志里到底发生了什么
- `zygote64` 反复 `SIGABRT`（`Abort message: '!(fd != -1)'`）、`init` SIGABRT：典型的 **root + 注入模块冲突**（Zygisk Next / LSPosed / mountify）导致的 zygote/system_server 崩溃；
- `Zygisk Next: failed to inject ... system server died` + 软重启：注入链路自身崩溃；
- `ksud::feature: Failed to set feature 10003: Invalid argument`、`KPM: ... Inappropriate ioctl for device`：**ksud 与内核模块版本/能力不匹配**（用户混用了不同版本的 ksud/LKM）；
- `fix_soft_reboot` 模块被禁用/卸载、`NukeExt4Sysfs /mnt/vendor/mountify`：用户在反复尝试“救”软重启，模块之间互相干扰。

### 11.2 根因排序
1. **模块冲突**（最主要）：Zygisk Next / LSPosed / mountify 与 KSU 同时加载，zygote 崩溃 → 软重启；
2. **ksud/LKM 版本不匹配**：feature 10003/KPM ioctl 失败，管理器与内核 UAPI 对不上；
3. **上游越狱流程本身的稳定性问题**：Loading 期调用 su、`packages.list` 加冕、3/4 LKM vermagic 错误、失败不中止（详见 §10）。

### 11.3 v2.4 已做的解决
- 新增 `CONFLICT_MODULES` 预检：模块加载后检查 `/data/adb/modules/{zygisksu,zygisk_next,lsposed,mountify,fix_soft_reboot,scene_systemless}`，发现即写入日志并提示“先禁用并重启再越狱”；
- UI 增加“模块冲突自检”说明卡；
- 统一 4 个 LKM 的 vermagic、删除 `packages.list` 加冕、增加 Live 等待/失败中止/临时文件清理；
- 默认不建 su overlay，减少检测面与额外挂载。

### 11.4 给群友的处置步骤（可直接转发）
1. 先退出反复重启：长按电源→长按“关机”→进安全模式；或连 ADB 后禁用冲突模块；
2. 到 KernelSU/SukiSU 管理器里**禁用/卸载**：Zygisk Next、LSPosed、mountify、fix_soft_reboot（以及任何 scene_systemless 类模块）；
3. 重启一次，确认只保留 root（无 Zygisk/LSPosed）；
4. 用 v2.4 重新越狱（首次进入会强制显示免费声明/赞赏码弹窗，属正常）；
5. 越狱后若要装 Zygisk/LSPosed，**逐个装、逐个重启验证**，不要一次全开；
6. 不要点管理器“直接安装/修补 boot”；不要用 `fix_soft_reboot` 这类模块去救——根因是模块冲突，不是重启逻辑。

### 11.5 如果仍然重启
- ADB 抓 `logcat -b crash -d` 与 `dmesg | grep -iE 'panic|kernelsu|zygisk|lsposed'`；
- 确认 ksud 版本与 LKM 版本一致（管理器“工作”页应显示版本/UAPI，不一致会提示）；
- 只保留本 App + 对应管理器，先不装任何其他模块跑 24h，再逐个加模块定位。
