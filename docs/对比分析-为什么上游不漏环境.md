# 对比分析：为什么上游版本不漏环境、应用授权正常，而我们的需要默认 SU 兼容层

> 结论先行：差别不在越狱链路/授权逻辑，而在**加载的内核 LKM 是从哪个内核源码编译的**。

## 一、两边用的 LKM 不是同一套

| 项目 | 内核 LKM | 文件大小 | 编译来源（vermagic 泄露） |
| --- | --- | --- | --- |
| 上游 KernelSU 官方 | ksu-base.ko | 349,224 B | 6.18.21-4k（按本机 6.18.21 源码自编） |
| 上游 BakaSU | ksu-base-bakasu.ko | 385,440 B | 6.18.21-4k（多管理器 + Tracepoint 钩子） |
| 上游 KernelSU-Next | ksu-base-next.ko | 350,000 B | 6.18.21-4k |
| 上游 SukiSU | ksu-base-sukisu.ko | 376,136 B | 6.18.21-4k（README：Tracepoint Syscall Redirect） |
| **我们的 KernelSU-Next 模板** | ksu-template.ko | 531,936 B | **6.18.32-4k-g47cc22554442-dirty** |
| **我们的 SukiSU 模板** | sukisu-template.ko | 406,294 B | **6.18.32-4k-g47cc22554442-dirty** |

你手机的运行内核是 `6.18.21-android17-5-gf957accaf563-ab15926176-4k`。
v2.3.3 沿用的这两个模板是**为 6.18.32 源码编译的**，不是本机内核。加载器靠 IGNORE_VERMAGIC 强制加载，所以“能加载”，但内核态 sucompat 是按 6.18.32 的结构/行为编的，在 6.18.21 上不完整：
- 应用进程直接 exec /system/bin/su → 能逃逸（我们实测通过）
- shell/PATH 调 su → EACCES（实测 /system/bin/su can't execute: Permission denied）

## 二、默认 SU 兼容层是谁带来的

- 上游仓库**完全没有** su_path_compat / su_forward / overlay：`grep -rn 'su_path_compat|onekey-su|su_forward' /tmp/yunni` 为空。
- 上游流程（exploit/scripts/run.sh）只有：ksud install → packages.list 加冕 → 重启管理器，**不创建任何挂载** → 天然不漏环境。
- 我们的 v2.3.3 血统自带 su_forward + su_path_compat.sh（OnePlus16-Jailbreak/app/assets 里就有，Java 引擎固定 stage 它们），因为它那套 LKM 的 sucompat 不完整，必须用 overlay 补 PATH 入口。
- 我们合并 v2.4 时把 v2.3.3 的模板 LKM 当成“已验证内核”沿用，因此也继承了“需要 overlay”的问题；overlay 一旦挂上，环境就露了。

## 三、运行时证据

| 指标 | 上游（BakaSU，用户截图） | 我们（SukiSU 模板） |
| --- | --- | --- |
| `ksud debug info` bundled | **true** | **false** |
| 默认 su 是否需要挂载 | 不需要 | 不开 overlay 时 PATH su 不可用 |
| /proc/mounts 痕迹 | 无 | 开默认 SU 后有 su_compat 挂载 |
| su 来源 | 内核原生 sucompat | 内核不完整 → 靠用户态 su_forward overlay |

## 四、我们的代码其实和上游一致的部分

- 越狱链：抓 slide → 反推 KASLR → 打 LKM 符号补丁 → permissive → cred → 两阶段写 → finit_module，完全同源（v2.3.3 = 上游链路前身）。
- 收尾：ksud install → packages.list 加冕 → 重启管理器，同上游；我们额外做 manager add/set-enabled（不影响隐藏性）。
- App 授权：都交给管理器写 allowlist，内核 sucompat 放行；差别只在**内核那半边是否完整**。

## 五、建议修复方向（待确认后再改代码）

1. 把 4 个管理器的内核全部换成**上游按 6.18.21 自编的 LKM**（/tmp/yunni 最新版）：
   - 官方 ksu-base.ko 349,224 / BakaSU 385,440 / Next 350,000 / SukiSU 376,136
   - 同时配对应 ksud（上游 assets 里已有）与对应管理器版本
2. 删除对 v2.3.3 模板（6.18.32）的依赖；
3. 默认 SU 兼容开关保持**默认关闭**，只有在确认某些应用/终端需要时才开；
4. 逐个管理器冷启动实测：管理器授权后 App 能否 su、/proc/mounts 是否无痕迹。

> 注：我们现在的 official/bakasu 分支用的其实已经是上游 6.18.21 LKM（只是版本较旧、被 vermagic 补过），Next/SukiSU 还在用 6.18.32 模板 —— 这正好解释“只有 SukiSU 要开 overlay 才 4/4，其他管理器修复老失败”的现象。
