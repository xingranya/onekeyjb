# 00 — 链路总览（CVE-2026-64560 → KernelSU LKM）

> 目标：在**未解锁 Bootloader、未刷任何分区、未重启**的前提下，从 `adb shell`（uid 2000、
> `CapEff=0`、SELinux Enforcing）拿到 `CAP_SYS_MODULE` + uid 0，并 `finit_module` 未签名的
> KernelSU LKM（越狱模式）。
>
> 全链只用一台**已授权 USB 调试的本人设备**，不依赖任何 App、不需要用户点确认。

## 一、七段链路

| # | 阶段 | 手段 | 拿到什么 | 关键前置 |
|---|---|---|---|---|
| 1 | 泄漏 KASLR slide | perfetto 使能 `sched/sched_blocked_reason`，读 `trace_pipe_raw`（shell 在 `readtracefs` 组）里的裸 64 位 `caller` | 本次启动的 `slide`，于是任意内核符号地址 = 链接地址 + slide | 无（零特权） |
| 2 | 任意地址零写 | CVE-2026-64560 悬空 `rb_node` + 8KB AF_UNIX frag 整页重占，走「只有左孩子」分支 | `*(T) = 0`（8 字节） | 无（零特权） |
| 3 | 关 SELinux | 上面那条零写打 `selinux_state`（`.bss`）头 8 字节 | `enforcing=0`、`initialized=0`（hook 全部早退） | 有 slide |
| 4 | kprobe 复活 | `kprobe_events`（0777）建探针；`enable`（`-rw-r-----`）用 code 7 root 写打开 | 任意内核 **8 字节读**（`@ADDR`）+ 任意进程 `task/real_cred/cred` 裸地址 | SELinux 已关 |
| 5 | 指名改 cred | 两阶段写：先把 `cred+0x48`（`cap_bset`）清 0，再把 `cred+0x40`（`cap_effective`）写成 `cred+0x40` 这个地址值本身 | 候选进程 `CapEff` 变成"cred 地址"，低位决定含哪些能力；挑 `bit16=1` 就含 `CAP_SYS_MODULE` | 有 cred 地址 |
| 6 | 装 LKM | vermagic 改写 + 225 个未导出符号 `SHN_ABS` 绝对化 → `finit_module` | `kernelsu ... Live` | `CAP_SYS_MODULE` |
| 7 | 用户态 | `ksud install`（uid 0 下）→ `/data/adb/ksu/bin/{su,ksud,busybox}` | root 命令执行器；`su` 需加载时 `allow_shell=1` | uid 0 |

## 二、漏洞本体（一段话）

`posix_cpu_timer_del()` 里 `lock_task_sighand()` 可能返回 `NULL`（目标线程正在 `exec`，
`sighand` 被换掉），老实现直接 `return 0` —— **没有把 `k_itimer` 从 `signal->cputimer`
红黑树上摘下来**。计时器对象随后被 `release_posix_timer()` 释放，`it.cpu.node` 成为
**悬空 `rb_node`**，仍挂在树上。之后目标进程退出时 `posix_cpu_timers_exit_group()` →
`cleanup_timers()` → `timerqueue_del()` 会对这个悬空节点做 `rb_erase` / `rb_next` /
`RB_CLEAR_NODE`。

修复在 6.18.41（`6a7ecc25abe6`），本机内核 6.18.21 **四个相关标记全部未回移**。

利用方式：让那块被释放的 `k_itimer` 所在页（`posix_timers_cache`，order-1，384B×21 对象、
步进 `0x180`）被我们的 **8KB AF_UNIX frag** 整页接管（`alloc_skb_with_frags` 在
`size=8192` 时走 `__alloc_pages(order=1)` 且 8192 字节逐字节可控），于是伪造 `rb_node`
的 `__rb_parent_color / rb_right / rb_left`，把 `rb_erase` 变成**写原语**。

## 三、两种"安全收尾"的树形状（全部实测）

```
形状 A（零写）            parent_color=0, rb_right=0, rb_left=T
  rb_next  → NULL（parent=0 且 right=0）        ⇒ 循环立刻结束，不污染 rb_leftmost
  rb_erase → 走 "!child" 分支                    ⇒ tmp->__rb_parent_color = 0 ⇒ *(T)=0
  RB_CLEAR_NODE(node)                            ⇒ *(node) = node  ⇒ 泄漏本页内核地址 P

形状 B（指针写）          parent_color=P, rb_left=0, rb_right=T
  迭代1 rb_next  → T（*(T+16)==0）              ⇒ head->next = T
  迭代1 rb_erase → *(T) = P，P->rb_right = T（页内）
  迭代2 rb_next(T) → 经 *(T+8)==0（已由形状 A 清过）上走到 P，返回 NULL
  迭代2 rb_erase → 只清 P->rb_right
  迭代2 RB_CLEAR_NODE(T)                         ⇒ *(T) = T
```

形状 B 的三个前提：`*(T+8)==0`（阶段 1 已清）、`*(T+16)==0`（`cap_ambient` 默认 0）、
页偏移 0 处放一个 `{1,0,0}` 假父节点。

## 四、为什么"能力位 = 地址的低位"

`cap_effective` 被写成 `cred+0x40` 这个**地址值**，所以能力集完全由 cred 落点决定：

```
bit0  CAP_CHOWN          bit7  CAP_SETUID        bit16 CAP_SYS_MODULE
bit1  CAP_DAC_OVERRIDE   bit8  CAP_SETGID        bit21 CAP_SYS_ADMIN
bit2  CAP_DAC_READ_SEARCH bit10 CAP_NET_BIND_SERVICE  bit19 CAP_SYS_PTRACE
```

`bit16` 约 1/2 概率为 1（地址第 16 位随机），所以一次起 8 个候选进程、挑一个
`((cred+0x40)>>16)&1 == 1` 的即可；`bit7/bit8` 同时为 1 时还能直接 `setresuid(0,0,0)`。

## 五、为什么必须走 KernelSU LKM（而不是 usermodehelper）

本机 `CONFIG_STATIC_USERMODEHELPER=y` 且 `CONFIG_STATIC_USERMODEHELPER_PATH=""` ——
`core_pattern`、`modprobe_path`、`uevent_helper`、cgroup `release_agent` **全部不执行**
（实测 `coredump: ... Core dump to |/system/bin/sh disabled`）。
而 `MODULE_SIG_FORCE` 未设、`__versions` 为空 ⇒ 未签名模块**可以** `finit_module`。
⇒ 拿到 `CAP_SYS_MODULE` 之后，"装一个能给我们 root 的模块"仍是本机最短路径。
