- root 收尾脚本以 root 自动清理旧的 /data/local/tmp/onekey 遗留给后续 shell 使用
- 失败也不会影响下一次运行

【v2.4.4】修复授权 root / su 用不了（su_compat + 管理器连接校验）
🐞 修复「刷完无法给软件授权 root / su 用不了」
- 原因：换用上游 6.18.21 自编 LKM 后，收尾脚本缺少两个关键步骤：

- 输出 manager list，可直接看到登记状态
- 新增「未授权 su 自检」：setpriv 降到 uid 2000 执行 su，日志里看 unpriv_su=0 即内核放行
- 越狱结束再补一条「原生 su 已放行 / 未放行」日志，出问题一眼定位
其他
- 继承 v2.4.3 的唯一工作目录修复（不再 Permission denied）

2. 重装当前管理器 APK
3. 软重启 Android 用户态：优先 ksud soft-reboot，失败回退 setprop ctl.restart zygote

【v2.5.2】su 通道修复（重建 /system/bin/su，不开默认 SU）
先理清「应用调 su」到底靠什么
Runtime.exec("su") / 终端 su 正常路径：
1. 应用调用 PATH 里的 /system/bin/su
2. KernelSU 内核模块（LKM）的 sucompat 内核钩子接管这次 exec
3. 按该应用 UID 查管理器的授权名单
4. 已授权 → 给 root 凭证，执行 ksud 提供的 su wrapper
所以三个条件缺一不可：LKM 已加载 + su wrapper 有效 + 管理器授权名单可写。
ColorOS 17 的安全机制（oplus_secure_guard 等）会把这个"原生内核调用"拦截/干掉，
表现就是终端 su: can't execute: Permission denied (126)、管理器授权了应用也用不了。
v2.5.2「su 通道修复」（等价 soft_reboot_core，但不需要装模块）

2. 重装管理器 APK（刷新内核侧管理器绑定，授权名单写入依赖它）
3. 关键：ksud soft-reboot 重跑 late-load stage 脚本，重建 /system/bin/su 的 kernel file wrapper
- 不是只 setprop ctl.restart zygote（只重启 zygote 不会重建 su wrapper）
- 失败才回退 restart zygote
4. 该修复集成在 run.sh 收尾里，以 root 执行；如果 shell 拿不到 root，会自动改用 KSU fd 方式重试
仍然不开默认 SU
- 「默认 SU 兼容」保持关闭，不创建任何 su_compat / system_ext 挂载，环境不暴露
- 修的是内核原生的 /system/bin/su 通道，不是 overlay

【v2.5.5】紧急修复 v2.5.4 自删工作目录问题
🐞 现象
v2.5.4 所有人越狱都报：

== 执行漏洞链（上游 run.sh） ==
sh: cd: /data/local/tmp/onekey-<时间戳>: No such file or directory
run.sh 退出码=2
内核模块未加载

🎯 原因（我自己写的 P0 清理误伤）
v2.5.4 新加的「清理旧残留」用了：
rm -rf /data/local/tmp/onekey-[0-9]*
但这段清理是在已经创建本次工作目录之后才执行的——本次目录名字正好是 onekey-<时间戳>，于是把自己的工作目录删掉了，run.sh 自然 cd 失败，模块根本没加载。
✅ v2.5.5 修复
1. 清理步骤移到「创建本次工作目录之前」执行 → 只清历史残留，不会误伤当前目录
2. 补回 ksu_grant 的投放（KSU fd 兜底修复需要它）
3. su_repair.sh 自删加保护：只有目录名是 /data/local/tmp/onekey_repair 才删除，避免极端情况下误删 /data/local/tmp
保留的 P0 内容（v2.5.4 原有，仍然有效）
- 清旧 su_compat / onekey-su 挂载与 /data/adb/onekey-su*
- 清 /data/local/tmp 临时残留
- 恢复 SELinux Enforcing
- 开启 selinux_hide / kernel_umount 特性
