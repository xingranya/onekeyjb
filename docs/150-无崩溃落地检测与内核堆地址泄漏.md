# 150 — 无崩溃的「落地检测 + 内核堆地址泄漏」原语（v23/v24）

日期：2026-10-17 23:58
设备：M610BB / SM8950 / Android 17 / 内核 `6.18.21-android17-5-g1d099fcb35e0`，补丁级 2026-09-01
漏洞：CVE-2026-64560（`posix-cpu-timers` 非 leader exec 竞态 UAF），上游修于 6.18.41

## 0. 本轮新增的两个东西

1. **不崩的落地判据**：把伪造节点的父指针设为 NULL，`rb_erase` 走最干净的路径，
   内核只把 `root->rb_node` 置 NULL、再把节点自身地址写回节点首 8 字节，
   **不 deref 任何伪造指针 ⇒ 命中且落地时不会 panic、不重启**。
2. **第一个真实的内核地址泄漏**：`timerqueue_del()` 末尾的 `RB_CLEAR_NODE(&node->node)`
   会把 `node` 自身的地址写进 `node->__rb_parent_color`。而节点就在我们的
   **8KB frag 页**上，这页是 socket 的数据页 —— `recv()` 读回来就能看到那个指针。

实测（`t64560_v23 250 400 16 6000 12000`）：

```
LEAK attempt=23  fd_idx=74   off=0xfe0  val=0xffffff89ad668fe0
LEAK attempt=60  fd_idx=221  off=0x1a60 val=0xffffff891b39fa60
```

两处都严格自洽：`off=0xfe0` → 值低 12 位 `0xfe0`；`off=0x1a60` → 低 12 位 `0xa60`。
即 `node 的虚拟地址 = 0xffffff89ad668fe0`、`0xffffff891b39fa60`，**线性映射区、无需 KASLR slide**。

## 1. 为什么这条路径是安全的（逐条对照内核代码）

伪造节点：`__rb_parent_color = 0`（parent=NULL、颜色红）、`rb_left = rb_right = 0`、`expires = 0`。

```
rb_erase_cached(node, root)
  if (root->rb_leftmost == node)
      root->rb_leftmost = rb_next(node);
          rb_next: rb_right==NULL → 跳过；parent==NULL → 循环不执行 → 返回 NULL   ← 不 deref
  __rb_erase_augmented(node, root):
      child = rb_right = NULL, tmp = rb_left = NULL
      parent = __rb_parent(0) = NULL
      __rb_change_child(node, NULL, NULL, root) → root->rb_node = NULL          ← 只写内核自己的堆
      rebalance = __rb_is_black(0) ? parent : NULL = NULL                       ← 不做颜色修复
  RB_CLEAR_NODE(&node->node) → node->__rb_parent_color = (ulong)node             ← ★ 泄漏点
```

## 2. 落地率（首次得到可信数字）

| 运行 | attempts | execs | 落地 | 结论 |
|---|---|---|---|---|
| v23（arm 3600s，退出路径） | 68 | 1088 | **2** | ≈ **3% / attempt ≈ 1/540 次 exec** |
| v22（arm 3600s，故意崩） | ≈150 | 2400 | 1（panic） | 1/2400 次 exec，同量级 |

每次 attempt 6 秒（16 victim × 400 计时器 + 排空 5~8s + 喷 6000 页），
所以现在是 **每 3~5 分钟一次落地**，且落地不重启设备 —— 迭代速度比之前快一个量级。

## 3. 顺带验证：写侧路径确实是干净的

`__rb_change_child(node, NULL, NULL, root)` 执行时 `root` 由内核提供（`&signal->cputimer`），
我们写的值是 NULL。也就是说 **"任意 8 字节零写"这条写路径已经跑通、且不崩**，
只是目标地址仍受限于「我们知道哪些地址」。

## 4. 试图再拿 `task_struct*`（v24，失败但结论明确）

`collect_posix_cputimers` 里有：

```
mrs  x8, sp_el0        ; current
add  x9, x22, #0x48
stlr x8, [x9]          ; *(node + 0x48) = current
```

即**计时器真的到点时**，内核会把 `current`（受害者自己的 `task_struct *`）写进我们那一页。
做法：把计时器 arm 成 600ms **CPU 时间**（排空期间受害者睡着，不累计 CPU，所以不会提前到点），
喷完页后用 `SIGUSR2` 让受害者烧 CPU 触发到期。

结果：跑了约 45 次 attempt 后设备在 **23:57:00 kpanic**，且之前没有出现任何 LEAK。
原因很清楚：**到期路径会把"没被我们接管"的悬空节点也走一遍**，
那种情况下节点早已被 posix cache 复用（22:30 那类 `list_add double add`），直接崩。
也就是说"提前到点"把一个 97% 安全的实验变成了会毁掉 boot 的实验，得不偿失。

⇒ 结论：**到期/collect 路径不能用来做泄漏**，除非先有办法确认"这一轮的页已经是我们的"。
可行的时序是：先用 v23 的方式（退出路径、arm 3600s）拿到 LEAK，确认落地之后，
再对**同一个 victim**制造一次到期动作 —— 但那时节点已被 `cleanup_timers` 摘掉，需要重新设计。

## 6. 下一步（按可行性排序）

1. **把 `collect` 的 `current` 写变成安全的**：先落地（v23 判据），**保持 victim 存活**，
   然后只对"已经落地"的那一轮做到期动作 —— 需要在 v23 的 LEAK 之后立刻给该 victim 烧 CPU，
   而不是像 v24 那样对所有轮次都提前到期。
2. **用已知的页地址换更多泄漏**：落地后，我们知道自己页的 VA，
   可以把该页用作"接收端"，让内核往里写指针（`list_add` 的 `head`、
   `collect` 的 `current`、`cpu_timer.pid`），逐次累积 ⇒ 最终拿到 `task_struct *`。
3. 有了 `task_struct *` 之后：`real_cred/cred` 在 `task+0x900/0x908`（BTF 实测），
   把 fake cred（放在我们已知地址的页里，uid=0/caps 全开）的地址写进这两个字段即可。
   注意 fake cred 需要 `user_ns`/`security` 等指针有效，稳妥做法是**先泄漏真实 cred 地址再改写其中字段**。
