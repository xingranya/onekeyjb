# 162 · out/ksu-op3.ko 静态校验（当前 boot slide = 0x28baa00000）

日期：2026-10-19 ｜ 设备：OnePlus 16 PYB110 ｜ 内核：6.18.21-android17-5-gf957accaf563-ab15926176-4k
目标：不碰设备，静态确认 out/ksu-op3.ko（ksu/ksunext.ko → next-v3.ko → op3.ko）能通过 6.18 内核模块加载检查。

## 0. 结论

**静态 PASS（可加载）**。除「运行时 sig_enforce 必须为 0」这一点外，所有可静态判定的加载门（vermagic、
227 个 SHN_ABS 符号、全量重定位范围、modversions、ELF 结构）全部通过。
同一套重打流程产出的 **out/ksu-op4.ko 已于 14:02 在本机 finit_module rc=0、/proc/modules 出现 kernelsu**，
旁证本报告结论（op3 与 op4 只差 Lead 追加的 cred/noenforce 补丁）。

上次失败（dmesg：`Modules: module kernelsu: overflow in relocation type 275 val ffffffe09a485e58`）已精确归因：
失败文件是 **out/ksu-op2.ko（按 0x2017c00000 打的）**，出问题的重定位是 `.init.text/.exit.text` 里对
`__tracepoint_sys_enter` 的 ADRP，`S+A = 0xffffffe09a485e58` 与 dmesg 值逐字节相同（见 §6）。

## 3. 重定位全量重算

全量 6286 条，按 v6.18 `arch/arm64/kernel/module.c: apply_relocate_add()` 的判定逻辑取值：
`val = S + A`；ADRP 判定 `(S 页 - P 页)` 是否落在 signed 21-bit（±4GB）；
P 的分布用内核自己选定的 module 区域（arch/arm64/mm/init.c `module_init_limits`）：
`direct_base ∈ [KIMAGE-0x5640000, KIMAGE]`、窗口 +128MB、模块自身段偏移 < 1MB。

| type | 名称 | 条数 | 内核检查 | 重算结果 |
|---|---|---|---|---|
| 257 | ABS64 | 290 | 无（overflow_check=false） | PASS |
| 260 | PREL64 | 61 | 无 | PASS |
| 261 | PREL32 | 1171 | signed 32 | 界 [-0x6d987c8, +0x69a7838] 在 ±2GB 内 PASS |
| 275 | ADR_PREL_PG_HI21 | 1401 | ±2^20 页 | [-32236, +32697] 在 ±1048576 内 PASS |
| 277 | ADD_ABS_LO12_NC | 1037 | 无（overflow_check=false） | PASS |
| 278 | LDST8_ABS_LO12_NC | 110 | 无 | PASS |
| 283 | CALL26 | 1815 | ±128MB，超界发 PLT | 1458 内核 ABS + 357 模块内；最坏 0x8096898 只出现在窗口极值，PLT 容量 1815 兜底 PASS |
| 284/285/286 | LDST16/32/64_ABS_LO12_NC | 401 | 无 | PASS |

**无 311/312（ADR_GOT_PAGE / LD64_GOT_LO12_NC），不存在 unsupported RELA 类型**，不会 -ENOEXEC。
ADRP 余量 32 倍的含义：模块区与内核镜像一起随 slide 平移，(S-P) 与 slide 无关；只有「ko 按别的 slide 打」时才会像上次那样超差。

## 5. `__versions` / modversions 为什么不是问题

- 本 ko：`__versions` size=0、`__version_ext_crcs` size=0、`__version_ext_names` size=1。
- 内核确实开了 CONFIG_MODVERSIONS（vmlinux 含 `check_version`/`check_modstruct_version`、字符串 `%s: no symbol version for %s`）。
- 但所有导入符号都被改成 SHN_ABS：`simplify_symbols()` 对 SHN_ABS 直接 break，**从不调用 resolve_symbol/check_version**，导入符号 CRC 比对整段被跳过。
- 唯一的 `module_layout` 版本检查：`check_modstruct_version()` → `check_version(info,"module_layout",mod,crc)`；
  因模块带 `__version_ext_crcs` 段（存在但 size=0），`info->index.vers_ext_crc != 0`，走 extended 分支，
  迭代 0 次后执行 `pr_warn_once("%s: no extended symbol version for %s")` 并 **return 1（成功）**。
- 结论：PASS；加载时 dmesg 预期出现一次 `kernelsu: no extended symbol version for module_layout` 之类 warning，非致命。
  （v6.18 源码：kernel/module/version.c:29-42、96-105；main.c:3320-3338 early_mod_check 顺序为 check_modstruct_version → check_modinfo。）

## 6. 上次失败精确归因

- out/ksu-op2.ko 的 ABS 值指向 slide=0x2017c00000（本文件 227/227 一致）。
- 在 op2 中搜 `S+A == 0xffffffe09a485e58`：恰有 4 条重定位命中，符号都是 `__tracepoint_sys_enter`
  （链接 0xffffffc082885e58 + 0x2017c00000 = 0xffffffe09a485e58），类型 275/277，目标段 `.init.text`/`.exit.text`。
- 换到当前 boot（P 约 0xffffffe93a…）：页差约 -9,000,000 页（约 -34GB），远超 ±4GB
  ⇒ 内核在第一条 type 275 上打印 `overflow in relocation type 275 val %Lx` 并返回 -ENOEXEC。
- ⇒ 该失败与 vermagic/签名/符号解析无关，**纯粹是 slide 没对上**；op3 已按当前 slide 重打。

## 7. 字节级 diff（vs out/ksu-op.ko、op2.ko）

- `cmp -l out/ksu-op.ko out/ksu-op3.ko`：681 字节，聚成 227 段、每段 3 字节；
  **全部位于 `.symtab` 中 227 个符号的 st_value 低 3 字节**，每个差值恒为 `0xCD1800000`
  （= 0x28baa00000 − 0x1be9200000 = 55,054,434,304 = 51.27 GiB）。
- op2 vs op3：681 字节、同样 227 个 st_value，delta 恒为 `0x8A2E00000`（= 0x28baa00000 − 0x2017c00000）。
- 三个文件的 `.modinfo` 段 sha1 完全相同（10e3c66b…），文件大小均 474454。
- ⇒ op/op2/op3 的差异**只有** slide 差值，无其它改动。

## 8. CONFIG_MODULE_SIG / 一加 MODULE_SIG_PROTECT

- vmlinux 有标准 CONFIG_MODULE_SIG 实现与符号：`module_sig_check`(0xffffffc080568120)、`sig_enforce`(0xffffffc08294f208, .bss)、
  `is_module_sig_enforced`、`module.sig_enforce` 参数；**sig_enforce 在 .bss ⇒ CONFIG_MODULE_SIG_FORCE 未设，静态默认 0**。
- 未签名 ko 被拒只发生在 `is_module_sig_enforced()==true` 时（v6.18 kernel/module/signing.c:119-122，返回 -EKEYREJECTED）。
  **ko 本身（vermagic/符号补丁）无法绕过它；必须运行时保证 sig_enforce=0。**
- 上一轮失败 dmesg 报的是 relocation overflow，而 module_sig_check 在 load_module 最前（+0x44）、relocation 在 +0x22f4，
  ⇒ 当时签名门已经通过（sig_enforce=0 或已被清零）；本轮 op4 rc=0 同样证明签名门未拦。
- 在 out/pyb110_vmlinux.elf 中**搜不到** `MODULE_SIG_PROTECT` / `protected_module_names_list` / `sig_protect` 字符串或符号，
  docs/160 里「一加私有 MODULE_SIG_PROTECT=y + 保护名单」的说法在本内核二进制中**没有证据**；实际就是标准 sig_enforce 开关。
- 行动项：无需改 ko；只要加载窗口内 `sig_enforce`（0xffffffc08294f208）== 0 即可。
