# 149 — ★★ 落地成功：悬空 rb_node 被我们的页接管（故障地址 = 我们布置的 0xdeadbeefdead0008）

日期：2026-10-17 23:28
设备：M610BB / SM8950 / Android 17 / 内核 `6.18.21-android17-5-g1d099fcb35e0`，补丁级 2026-09-01
漏洞：CVE-2026-64560（`posix-cpu-timers` 非 leader exec 竞态 UAF），上游修于 6.18.41

## 0. 一句话

**UID 2000 的普通进程，把悬空的 `k_itimer.timerqueue_node` 所在 order-1 slab 页
用 8KB 的 AF_UNIX frag 页整页接管，并让内核在 `rb_next()` 里解引用我们伪造的指针，
故障地址正是我们写进去的 `0xdeadbeefdead0008`。**
这不是"又一个 panic"，而是**「抢页 + 内容完全可控」的硬证据**——写原语的入口。

## 3. 关键结构（对齐参考实现后补齐的三件事）

参考实现 `plz110-6.12.69-cve-2026-64560-ksu` 的节奏是：每次 attempt **16 个 victim**、
**轮询 `/proc/slabinfo` 的 `posix_timers_cache` 等待排空**、然后喷大批 8KB frag。
我们此前缺的正是这三点，`t64560_v22` 全部补上：

1. **`race_batch = 16`**：每次 attempt 并发 16 个 victim（各自独立的计时器组与删除风暴），
   命中率是单 victim 结构的 16 倍；
2. **排空判据（可测，不靠猜）**：
   ```
   严格门：active <= baseline+64 且 total <= baseline+64
   宽松门：active < 1200 且 total < 1200，等 8s 后放行（系统自身计时器会让 active 漂移）
   ```
   实测：6400 个计时器建完删完，**1215~8100 ms 内** `posix_timers_cache` 从 399/420 回落到基线附近
   ⇒ 空 slab 确实被 SLUB 归还到 buddy；
3. **排空后才喷 6000 个 8KB frag**（48 MB），把刚回到 buddy 的 order-1 页抢走，
   然后逐个 `SIGKILL` victim —— 退出即 `posix_cpu_timers_exit_group → timerqueue_del → rb_erase`。

```bash

adb shell "/data/local/tmp/t64560_v22 200 400 16 6000 12000"
```

- 每次 attempt ≈ **6 秒**（16 个 victim、6400 个计时器、排空 1~8s、喷 6000 页）；

## 6. 下一步（写原语）

这次的 `rb_next` 只做了**读**（`parent->rb_right`）。要做写，需要让结构走
`__rb_erase_augmented → __rb_change_child(node, new, parent, root)`：
它会执行 `parent->rb_left == node ? parent->rb_left = new : parent->rb_right = new`，
即"把受控 8 字节写到受控地址"。要点：

1. 给节点设置 **非空 `rb_left`**（或 `rb_right`），逼内核走双分支路径；
2. `parent` 指向「目标地址 − 0x10（rb_left）或 − 0x8（rb_right）」，
   且该处必须可读（第一次比较要读得到），否则会像这次一样在读侧先崩；
3. 真正的目标是 `cred`（把 `uid/gid` 四元组与 `cap_*` 一起改），
   但**需要一个内核地址**（cred 的地址）——这是我们尚未解决的泄漏问题。
   可行的泄漏方向：① 利用同类 UAF 把 `timerqueue` 的节点指针读回到用户态（`timer_gettime` 路径）；
   ② 用参考实现的 `configfs/uhid` 桥把任意读做出来（工作量大）。
