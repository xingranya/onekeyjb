# 13 · 踩坑与修复记录

按「症状 → 根因 → 修法」记录，避免重复踩。

## 热切换相关

### 1. 装了通用模块开关、越狱也成功了，但 `/proc/kernelsu_manager` 不存在

**根因**：引擎按固定路径取 `libksud.so`，且 `PYB110_KSUD` 被忽略；线上跑的其实是管理器自带的单管理器 LKM。
**修法**：改为"替换管理器目录下的 `libksud.so`"为内置通用加载器，重启后生效。

### 2. `rmmod kernelsu` 失败，想热替换模块做不到

**根因**：模块引用计数 > 0，内核拒绝卸载（`Try again` / EBUSY）。
**结论**：通用模块只能在**开机后第一次**加载，必须重启，别指望运行时替换。

### 3. 打开开关、重启、再跑一次，仍然没有节点

**根因**：这一轮之前已经加载过单管理器模块（`late-load` 见到已存在就静默跳过，还返回 0）。
**修法**：运行前检测"已加载 kernelsu 且无节点"直接拦截，提示重启；加载结果落盘回读，日志区分成功/未生效。

### 4. 切换后五个管理器全部显示"工作中"

**根因**：上游 BakaSU profile 会注册所有已安装的静态管理器（设计如此）。
**结论**：以面板里的 `primary：…` 原文为唯一判据；切换后强制停止全部管理器，重开才刷新。

### 5. 目标选择完弹窗直接关掉，还得再点一次热切换

**根因**：选择回调里把抽屉关掉了。
**修法**：选完 `sheet = 1` 回到热切换面板本身（抽屉保持可见，不重新播入场动画）。

## 抽屉/界面相关

### 6. 切换开关时整个抽屉"弹一下"

**根因**：抽屉实例化在列表 item 内、`visible` 状态局部创建，内容变化时被重建/高度动画重跑。
**修法**：抽屉合并为单一实例、`visible` 提到根级、每个面板给固定高度。

### 7. `WindowBottomSheet` 完全不显示

**根因**：初始 `show` 就是 true，入场动画没有起点。
**修法**：`var v = remember { false }` + `LaunchedEffect { v = true }`，再由 `v` 驱动 `show`。

### 8. 分组卡片比自绘卡片窄一圈

**根因**：页面 `contentPadding` 已给 12dp，`ListCard` 内又加了一层 `padding(horizontal = 12.dp)`。
**修法**：去掉组件内边距，统一由页面给。

### 9. 深色下设备卡/运行卡发灰黑、与其它卡片不一致

**根因**：自绘卡片用了自定义色，`ListCard` 用 COUI 的 `surfaceContainer`，两套颜色。
**修法**：新增 `oneKeyCardColor()`（直接取 COUI `surfaceContainer`）与 `oneKeyDeviceColor()`（其上叠主色）。

### 10. 顶栏文字被内容盖住 / 模糊把文字糊掉

**根因**：三层都用 `matchParentSize()` 导致高度塌陷；`DstIn` 淡化作用到了文字层。
**修法**：只让内容层决定高度；模糊层、scrim、文字层分开，淡化只作用于模糊层。

### 11. 软重启后显示"未越狱"，热切换不可用

**根因**：引擎成功后立刻软重启，进程来不及写状态。
**修法**：收到 `SU_ID_RC=0` 立即同步落盘 `success_boot_id`（`commit()` 而非 `apply()`）。

### 12. 未启动 Stellar 时点开始直接闪退

**根因**：读 `/proc/sys/kernel/random/boot_id` 的调用写在 `try` 之外。
**修法**：包进 `runCatching`，读不到就不阻断，交给服务检查提示。

## 引擎/日志相关

### 13. 越狱卡死、等一分钟手机自动重启

**根因**：`cred` 阶段回收没落地（`RECLAIM_FREED=0`、`HIT=0`）时引擎仍盲写 4096 次并反复重试，把内核拖挂。
**修法**：按"每次尝试"计数，连续 4 次未命中即中止；中止后尝试 `setenforce 1` 恢复；失败且已写入内核则记 boot_id，下次先要求重启。

### 14. 一次失败被当成两次

**根因**：同一次尝试会同时输出 `HIT=0` 与 `rc=-1` 两行，按行计数就翻倍。
**修法**：只按 `rc=-1` 计一次。

### 15. 构建期 Kotlin 注释里的 `/*` 把代码吃掉一半

**现象**：写 `lib/arm64/*.so` 到 KDoc 里，报 "Unclosed comment"。
**根因**：Kotlin 块注释可嵌套，`/*` 会开新注释。
**修法**：文档里避免出现 `/*` 序列（改写措辞或断行）。

### 16. 用脚本按行号整段搬运代码，导致大面积删除

**教训**：文件改过很多轮后行号不可靠，切片容易切错。
**做法**：改代码一律用**函数名/唯一注释做锚点**，先备份，改完立刻编译；一次只动一个函数。

## 发布相关

### 17. CI 报 `Keystore file not set for signing config release`

**根因**：仓库不含 `keystore.properties`（已 gitignore），签名配置却无条件创建。
**修法**：`build.gradle.kts` 里按文件是否存在条件启用签名；本地发版时手动放入 `keystore.properties` + keystore。

### 18. 未签名包能装但装上后拒绝执行

**原因**：`SecurityCheck` 校验安装包签名指纹，非本项目签名的包一律拒绝。

### 20. 「越狱后软重启」开关拨了没反应，开与关都照样重启

**症状**：拓展功能里的「越狱后软重启」无论开还是关，越狱成功后系统都会重启一次。

**根因（三条叠加）**：
1. 开关只做了两件事：写 prefs、把 `PYB110_SOFT_REBOOT` / `PYB110_REBOOT` 拼进引擎环境变量；而引擎**根本不读这两个变量**（引擎的 `PYB110_` 全集里没有它们），所以开关是死开关。
2. 应用自身也没有任何重启调用（`RestartManager.request()` 零调用点），所以"没有自动重启代码"并不等于"不会重启"。
3. 真正扰动系统的是成功后的 `hardenAfterSuccess()` → `Safer.disable()`：它执行 `pm disable-user com.coloros.securityguard` / `com.oplus.safecenter`，改的是 PackageManager 数据，ColorOS 上很容易连带 system_server 重启；同时 `unloadKernelGuard` 默认开会去 `rmmod oplus_secure_guard_new`。

**修法**：
- 软重启改为**应用侧显式动作**：`softRebootAfter` 默认 false，只有开关打开且越狱成功才执行一次 `su -c 'setprop ctl.restart zygote'`，并用 `softRebootIssued` 保证单次运行最多一次；关闭时只记一行「保持当前会话不重启」。
- 安全组件从 `pm disable-user` 改为 `am force-stop` + `stop riskdetect`，不改包状态。
- `antiRootGuard`、`unloadKernelGuard` 默认改为 false。

**教训**：给引擎传环境变量前，先在二进制里数一遍该变量出现次数；0 次就是没人读，别指望它生效。

### 21. 上游 runner 换了命名与协议，包装脚本可以退役

**现象**：通用多管理器模块靠一段 shell 包装脚本 + `PYB110_KSUD` 假接线实现，脆弱且 `--kmi` 写死 `android17-6.18`。

**根因**：我们内置的引擎是上游改名前的旧构建（`usage: t98260 run`），不支持 `PYB110_UNIVERSAL`。

**修法**：换用上游 v2.1 的 `libk61821.so`（`usage: k61821 run | ksud | __plant`，451,536 B，SHA-256 `4c88a76a…`），env 增加 `PYB110_UNIVERSAL=1` / `PYB110_UNIVERSAL_KSUD` / `PYB110_SUSFS_KO` / `PYB110_VFS_KO`，`PYB110_KMI` 改由 `DeviceProfiles.kmi` 提供；删除 25 行包装脚本。

### 22. 引入外部 PoC 源码没补署名，且漏查了无扩展名的 assets 二进制

**症状**：上游作者在其他仓库连提三个 issue 要求补 MIT 署名；自查发现本仓库同样命中。

**根因**：
1. `cpp/ghostkey/pc98260_su.c` / `pc98260_rootd.c` 改编自 MIT 项目，保留上游 80/83 与 87/100 非空行，但文件头无版权行，声明文件里也没有原项目链接与 MIT 全文。
2. 第一轮排查只搜了 `*.so` 与 `libcve98260*`，**漏掉了无扩展名的 `assets/ghostkey/ghostkey98260`**，误判成"产物未分发"。
3. 进一步复扫发现 `onuce_*` 载荷也内嵌同一 rootd 实现（含 `[rootd] startup failed errno=%d (%s)` 原文与源文件名 `pc98260_rootd.c`）。

**修法**：
- 删除 ghostkey 全套与 4 个 onuce 载荷，改用上游按内核拆分的 Shark runner（6.18.21 / 6.12.69），二者均不含该 MIT 部分；
- 补 `LICENSES/MIT-pc98260.txt`（上游 LICENSE 原样）+ 声明第五节历史署名与来源链。

**教训**：
1. 排查二进制来源时**按内容扫全部 assets 文件**，不要按扩展名过滤——可执行产物常常没有后缀；
2. 删 HEAD 不追溯既往：历史提交与已发布 APK 仍构成"分发"，署名不能省；
3. 删资产前先查回退分支：`GhostKeyEngine` 投放失败返回 `false` 而非 `null`，只删文件会让调用方不回退，直接坏掉。

### 23. grep 被 head 截断，把活代码误判成死代码

**症状**：审计时判定 `Prep.java`（384 行）为零引用死代码，准备删除。

**根因**：核实命令写成 `grep -nE "\bPrep\b|..." ShizukuShell.java | head -5`，
5 条 `ProcessRunner` 命中占满了输出，真正的第 159 行 `Prep.readAsset(in)` 被截掉。
而 `ShizukuShell.stageAsset` 每次资产投放都走这一行 —— 删掉 `Prep.java` 会让整个 App 的投放全挂。

**修法**：先把 `readAsset` 内联进 `ShizukuShell`（改名 `readAssetBytes`），再删 `Prep.java`。

**教训**：**判断"是否死代码"的 grep 一律不加 head/tail 截断**；
输出长就换更精确的模式或按文件分组，绝不能靠截断后的前几条下结论。

### 24. 越狱后残留进程杀不掉：shell 身份杀不了 root cred 的 holder

**症状**：越狱成功后进程管理器里长期残留两个 `onekey-98260`（实测 PID 17418 / 17462）。

**根因**：
1. 收尾用 `pkill -9 -f onekey-98260; true`，以 shell（uid 2000）身份执行；
2. 上游 `plant_core.inc` 用 `prctl(PR_SET_NAME, "t98260-hold" / "t61269-hold")` 给 parked 子进程改名，
   并让它持有提权后的 **root cred** → shell 杀 uid 0 进程返回 EPERM；
3. 末尾 `; true` 把失败吞掉，日志里看不出任何异常；
4. 而且 `finally` 的清理跑在 `su -c id` 校验**之前**，顺序反了。

**修法**：
- 先验 root（`su -c id` = 0），再清理；
- 清理用 root 身份，且 **cmdline + comm 双路匹配**：`pkill -f` 之外再遍历 `/proc/*/comm`
  命中 `t98260-hold|t61269-hold|yexec` 逐个 `kill -9`；
- 用 `echo KILL_DONE` 做回执，收不到就记日志，不再 `; true` 静默。

**教训**：杀"自己启动的进程"也要考虑它可能已经提权；
`prctl` 改的是 comm 不是 cmdline，只按 `-f` 匹配会漏。

### 25. 「回退通道」的后端其实没实现，回退等于注定失败

**症状**：审计发现自研执行器回退分支不可达，计划把它改成「运行失败后回退」。

**根因**：读 `native/executor/main.c` 才发现
- `:54` `if (access(sym, R_OK) != 0)` → preflight 强制要求符号表；
- `:66` `printf("ERROR=plant 尚未实现（M2 进行中）")` → **plant 阶段根本没写**。

也就是说 `onekey-exec run` 永远走不到加载模块，回退只会稳定产生一次注定失败的重试。
原计划「修回退」的前提不成立。

**修法**：改为**删**——移除 `NativeExecutor.kt`、回退分支、`onekey-exec` 与两份符号表，
执行器成为唯一通道；`native/executor/` 源码保留作为 M2 的 WIP，但不随包分发。

**教训**：
1. 决定"修还是删"一条通道前，**先读它的后端实现**，别只看调用侧的分支条件；
2. 压缩率会骗人：13.08 MB 的文本符号表删掉后，APK 只小了 2.71 MB —— 
   **估算安装包收益要看压缩后，不能拿未压缩字节直接减**。

### 26. 按花括号配平提取函数时，签名里的默认 lambda 参数会被当成函数体起点

**症状**：拆分 MainActivity 时，提取器把 `BlurBar` 截成 11 行（实际 34 行），
生成的新文件编译报一堆 Unresolved reference。

**根因**：`BlurBar` 的签名含默认 lambda 参数
`onHeight: (Int) -> Unit = {}`。提取器从声明行开始数花括号，
参数列表里的 `{}` 被当作函数体开始，配平后立刻判定结束。

**修法**：先跳过声明自身的**参数列表**（圆括号配平）再开始数花括号。
修好后全量扫 52 个顶层声明，只有这一处受影响。

**教训**：
1. 写代码提取/搬迁工具时，**必须对全部目标声明做边界自检**（首行是签名、尾行是 `}`、行数与预期比对），
   不能只抽查几个；
2. 搬完要做**逐字保真断言**（`to_internal(原文) in 新文件`）与**符号守恒断言**
   （新集合 == 旧集合 − 已知删除项），这两条能同时挡住搬漏、搬重、截断；
3. 跨包搬迁还要补同包符号的 import（如 `BuildConfig`、`R`），
   原文件同包不需要 import，搬走后就缺了。

### 19. GitHub push 偶发 `TLS connect error / unexpected eof`

**处理**：重试即可（网络问题，不是仓库状态问题）；长命令用后台任务，避免前台超时把任务打断。

### 27. 中文日志分级：否定式和肯定式共用词根，顺序写错就把失败显示成成功

**症状**：日志分级上线后，「连续 4 次尝试未成功」被标成**成功**（绿色）。
比不分类更误导——用户以为跑通了。

**根因**：`classify()` 里先判 `line.contains("成功")` 再判否定式，
而「未成功」本身包含「成功」两个字。同理「未完成」含「完成」、
「未找到」含「找到」、「未发现已知冲突」含「发现」。

**修法**：判序固定为 ①特例白名单 ②特例黑名单 ③否定式/故障词 ④未完成类 ⑤肯定式。

```kotlin
if (line.contains("未发现")) return LogLevel.SUCCESS                       // 结论良好
if (line.contains("发现已知冲突") || line.contains("发现冲突")) return LogLevel.ERROR  // 词序反转就是坏消息
return when {
    // ③ 否定式与故障词
    line.contains("未成功") || line.contains("没有成功") || line.contains("不成功") ||
        line.contains("失败") || line.contains("中止") || line.contains("错误") ||
        line.contains("未安装") || line.contains("未运行") || line.contains("没有可") ||
        line.contains("不在列表") || line.contains("已不在") ||
        line.contains("找不到") || line.contains("未找到") ||
        (line.contains("未") && line.contains("找到")) ||   // 兜「未在…里找到 ksud」这种语序
        line.contains("rc=-1") || line.contains("FAIL=") || line.contains("MISSING") -> LogLevel.ERROR
    // ④ 未完成 / 被拦下 / 需要用户操作
    line.contains("未完成") || line.contains("警告") || line.contains("提示：") ||
        line.contains("跳过") || line.contains("未开启") || line.contains("不可用") ||
        line.contains("超时") || line.contains("未获得") || line.contains("暂不") ||
        line.contains("未命中") || line.contains("已断开") || line.contains("不能") ||
        line.contains("请先") || line.contains("正在切换") || line.contains("运行中") -> LogLevel.WARN
    // ⑤ 肯定式
    line.contains("成功") || line.contains("完成") || line.contains("已加载") ||
        line.contains("已用") || line.contains("补齐") || line.contains("已接管") ||
        line.contains("已归一化") || line.contains("已授予") ||
        line.contains("DONE") || line.contains("MODULE_LOADED") -> LogLevel.SUCCESS
    else -> LogLevel.INFO
}
```

**教训**：
1. 中文否定式**不换词**，只在前面加「未/没有/不」，所以子串匹配一定会撞车。
   凡是用 `contains` 做中文语义判断，必须先枚举否定式再判肯定式；
2. 语序会骗人：「未找到 ksud」能匹配「未找到」，
   但「未在管理器 APK 里找到 ksud」不能——要 `contains("未") && contains("找到")` 双条件兜；
3. 重试提示（「第 2 次尝试未命中，继续重试」）不是终态失败，归 WARN 不归 ERROR；
4. 这类规则必须配**真实日志行回归测试**（`classifyRealLogLines`），
   把项目里每一条 `addLog("...")` 的原文抄进断言，否则改一个字就静默回归。

### 28. 历史页满屏「未完成 0.00s」：append 在无 activeId 时凭空建记录

**症状**：历史页每开一次 App、每拨一次开关，就多一条
「98260 运行链 · - · 未完成 0.00s」，用户以为程序一直在失败。

**根因**：`HistoryStore.append(line)` 开头写着
`if (activeId == null && line.isNotBlank()) { start(ctx, "unknown", "-", false, "") }`。
设计意图是「只要有日志就该有记录」，实际效果是**任何一句 addLog 都会新开一条记录**，
而记录只有在 `finish()` 被调用时才会离开 running 状态。
开关操作、退出 App、软重启打断——都不会走 finish，于是全部沉淀成「未完成」。

**修法**：
1. `append()` 改为 `val id = activeId ?: return`——没有进行中的运行就不记账；
2. 新增 `abandon(context, reason)`：启动时把残留的 running 记录标成 `interrupted`（异常中断），
   这样历史页显示的是「异常中断」而不是「未完成」；
3. 新增 `stats(context, recent)`：只把 `ok` / `failed` 计入分母，
   `interrupted` 不入分母（被打断的样本不该拉低成功率）；
4. `RunLog` 侧给 `addLog` 加 `toHistory: Boolean = HistoryStore.hasActive()` 默认值，
   让「写日志」和「记账」彻底解耦。

**教训**：日志存储里任何「自动补建父记录」的兜底都是危险的——
它把「写日志」这个高频无害动作变成了「创建业务实体」。
兜底要往**收敛**方向写（没有就丢弃），不要往**扩张**方向写（没有就新建）。

### 29. 软重启把进程连根拔掉，finally 一行都跑不到——只能靠墓碑

**症状**：越狱后系统重启，日志里完全没有归因信息，
只能靠下次启动看 `boot_id` 变了，知道「重启过」，但不知道「重启发生在哪一步之后」。

**根因**：`ksud soft-reboot` / `setprop ctl.restart zygote` 直接重建用户态，
Java 进程被 SIGKILL，`finally`、`catch`、`onDestroy` 全部不执行。
任何「事后归因」的代码都注定跑不到。

**修法**：`RunTrace.mark(context, stage, intentional)` ——
每进入一个阶段就往 `filesDir/onekey-run-trace.json` 写一份墓碑
（stage / boot_id / 时间戳 / intent 位），`FileOutputStream` 写完 `flush()` + `fd.sync()`。
下次启动 `RunTrace.settle(context)` 读墓碑：
- boot_id 变了且 `intent=false` → WARN「上次运行在「X」之后系统重启」+ 该阶段的可操作建议；
- boot_id 变了且 `intent=true` → INFO「按设置软重启，属正常收尾」；
- boot_id 未变 → 返回 null，交给 `HistoryStore.abandon` 处理。

`intent` 位是必须的：用户自己开的软重启不该被报成异常重启，否则归因自相矛盾。

**教训**：**能活过进程死亡的只有文件**。
要做「崩溃/重启归因」，别指望 try-finally，
在**每个阶段边界**主动落盘一个带 `fsync` 的小文件，成本几毫秒，收益是唯一证据链。
落盘后记得在正常收尾路径 `clear()`，否则下次启动误报。

### 30. COUI alpha17 要求 compileSdk 37.1+，`disableCompileSdkChecks` 是绕过不是修复

**症状**：升到 `io.github.itoseo:coui:0.0.1-alpha17` 后
`:app:checkReleaseAarMetadata FAILED`，报 5 条
`requires compile against version 37.1 or later`，而项目是 `android-37.0`。

**根因**：读 aar 内的 `META-INF/com/android/build/gradle/aar-metadata.properties`：
COUI alpha17 是 `minCompileSdk=37` + `minCompileMinorSdk=1`；
compose 1.13.0 是 `minCompileSdk=37` + `minCompileMinorSdk=0`。
项目当时 `compileSdk { version = release(37) { minorApiLevel = 0 } }`。

   确实能让 checkReleaseAarMetadata 过、assembleRelease 也成功，
   但这是关掉体检，不是治病；
2. `sdkmanager --list` 在 channel 0/1/2/3 下都只有 `platforms;android-37.0`，官方源不提供 37.1；
3. `curl https://dl.google.com/android/repository/repository2-3.xml` 本机直接不通。

**修法**：
1. 本机 `~/Library/Android/sdk/platforms/` 里已装 `android-37.2`，直接用它；

4. 删掉 gradle.properties 里的 `disableCompileSdkChecks`；

报错不说 minor，容易让人以为要装 37.1 而实际上 37.2 也行。

### 31. 查 APK 里有没有中文串，`strings` 和 `grep -a` 都查不到

**症状**：`strings classes.dex | grep 成功率` 返回空，
差点误判「R8 把资源删了 / 中文没打进去」。

**根因**：`strings` 默认只输出可打印 ASCII，
UTF-8 中文是多字节非 ASCII，整串被跳过；`grep -a` 同样按行匹配，
而 dex 里字符串区没有换行分隔，整块被当成一行，超长行会被 grep 截断/放弃。

**修法**：用 Python 直接读字节做子串计数：

```python
import zipfile
z = zipfile.ZipFile(apk)
blob = b''.join(z.read(n) for n in z.namelist() if n.endswith('.dex'))
for s in ["本次成功率", "内存占用", "关于成功率的说明"]:
    print(s, blob.count(s.encode('utf-8')))
```

注意用 `/opt/homebrew/Caskroom/miniforge/base/bin/python3`
（本机 `/opt/homebrew/bin/python3` 不存在）。

### 32. R8 混淆后按类名查 APK 内容必然为 0，要查 mapping.txt

**症状**：`unzip -l app-release.apk | grep -c com/itos/coui` 返回 0，
`strings classes.dex | grep itos/coui` 也是 0，怀疑 COUI 没打进去。

**根因**：release 开了 R8，`com.itos.coui.sheet.BottomSheetKt` 被重命名成 `pe:` 这类短名，
原始包路径只留在 `mapping.txt` 里。

**修法**：查 `app/build/outputs/mapping/release/mapping.txt`：

```bash
grep -c "^com.itos.coui.sheet" app/build/outputs/mapping/release/mapping.txt
# 50
```

50 行命中即证明 BottomSheet 相关类全部进包。

**教训**：release 包的内容校验分两类——
**字符串**用字节计数（见 31），**类/符号**用 mapping.txt。
两者都不能拿 debug 包的经验套。
### 33. 日志页一点就闪退：CouiShape 圆角权重必须 ≥ 2

**症状**：点底栏「日志」立刻闪退，历史页正常。

**根因**：crash buffer 首行
`java.lang.IllegalArgumentException: 圆角权重必须为有限值且不小于 2, 与轮廓 Shader 保持一致`。
`CouiShape(radius: Dp, cornerWeight: Float)` 在构造期 `require(weight >= 2f)`，
而日志页两处写了 `1f`：

```kotlin
.clip(CouiShape(2.dp, 1f))   // LogRow 左侧等级色条
.clip(CouiShape(4.dp, 1f))   // LevelTag 标签底
```

**修法**：全部改 `2f`。全仓 32 处 CouiShape 调用只有这两处是 1f。

**教训**：COUI 的 cornerWeight 是给轮廓 Shader 用的平滑参数，不是圆角比例；
下限 2 是硬性 `require`，越界直接抛异常而不是降级。新增形状先搜一遍同类调用。

### 34. 弹窗「消失瞬间没了」：`if (show)` 把退场动画的子树拆了

**症状**：弹窗弹出有从下往上的动画，点「知道了」瞬间消失，没有收起动画。

**根因**：COUI 的窗口动画由 `visible` 参数驱动，库内部用 `retained` 标记
（`CouiDialogWindow.kt`：`if (visible != null && !visible && !retained) return`）
在动画期间把窗口留在组合里。调用方写 `if (show) Dialog(...)`，
show 变 false 的同一帧子树就被摘掉，窗口跟着销毁，动画来不及跑。

**修法**：新增 `DialogSlot(visible) { ... }` 宿主——弹窗常驻组合，只在隐藏后多留 320ms
再撤掉；九个弹窗全部加 `show: Boolean = true` 首参并把 `show = true` 改成 `show = show`。
更新弹窗还要留住最后一次的 `Info`（`lastUpdateInfo`），否则关闭后没有数据可渲染退场帧。

**验证**：`screenrecord` 录屏 + 逐帧算像素差，退场期间存在中间帧（弹窗已下滑一段、背景已亮）。

**教训**：凡是库用「状态 + 保留窗口」实现动画的，调用方就不能用条件组合代替状态参数。

### 35. 抽屉点了没反应：首帧 `visible` 仍是 false，自己把自己关了

**症状**：管理器热切换 / 管理器 / 管理器下载 / 拓展开关四个抽屉按下后都不显示。

**根因**：`WindowBottomSheet` 里 `LaunchedEffect(visible.value) { if (!visible.value) onDismissFinished() }`，
首次组合时内部 `visible` 还是初始 false（外部 `sheetVisible` 的置位与组合同帧赛跑），
立刻回调 `onDismissFinished` → 外部把 `sheet` 置 0 → 抽屉刚建就关。

**修法**：加 `everShown` 门控——只有真的显示过才允许触发关闭回调；并 `delay(EXIT_MS)`
等收起动画跑完再复位，否则内容会在动画途中被清空，看起来像「缩没了」。

### 36. COUI 动作区只有两个按钮时会并排，还会把次要动作染红

**根因**（`Dialog.kt:75-81`）：

```kotlin
val verticalOrder = listOfNotNull(neutralAction, confirmAction, dismissAction)
val horizontal = neutralAction == null && dismissAction != null
val actionRows = if (horizontal) listOf(listOfNotNull(dismissAction, confirmAction))
                 else verticalOrder.map { listOf(it) }
```

两件事同时发生：① 只给 confirm+dismiss 时 `horizontal = true`，两个按钮并排成半宽，
和环境诊断那种整宽按钮不搭；② `destructiveAction = neutralAction`，
进了 neutral 槽的动作会被套上 `colors.destructive`（红字）。

**修法**：`WindowDialog` 把第一个次要动作塞进 `neutral` 槽（`horizontal` 恒为 false，永远纵向堆叠），
并给次要动作**显式提供** `CouiDialogActionColors`——
`DialogActionButton` 里是 `colors = action.colors ?: DialogButtonDefaults.secondaryColors(...)`，
自己给了配色就不会再被 destructive 覆盖。

**教训**：判断一个库的布局分支，去读它的 `if/else` 判据，不要看渲染结果反推。

### 37. 弹窗左右缩进各写各的：24 / 24+14 / 16 三种，摆一起像两套 UI

**症状**：用户手册、第三方组件说明、免费声明与赞赏码、用户条款四个弹窗
跟环境诊断的弹窗「不搭」。

**实测**（1080 宽 @420dpi，弹窗左边界 x=67）：

| 弹窗 | 内容左边界 | 换算 | 来源 |
| --- | --- | --- | --- |
| 环境诊断 | 117 | 19dp（16dp + 图标留白） | `Column` 无内边距，行用 `BasicComponent`（库内 16dp） |
| 第三方组件说明 | 132 | 25dp | 外层 `CouiDialogDefaults.contentPadding`（24dp） |
| 用户手册 | 193 | 48dp | 外层 24dp + 卡片内 14dp |

**修法**：定义 `DialogInset = 16.dp`（与环境诊断的 `Item` 内部内边距一致），
所有弹窗内容槽一律用它；`ManualSection` 去掉 Card 改扁平排版；
按钮区靠 36 那条改成纵向堆叠后，与环境诊断的整宽按钮完全同形。

**教训**：**`CouiDialogDefaults.contentPadding` 是给 title/message 槽用的，不是给 content 槽的**。
content 槽没有内边距，加了就比库自带的 `Item` 多缩进一圈。

### 38. `/proc/slabinfo`、`/proc/loadavg`、sysfs 温度普通 App 读不到

**症状**：内存占用、CPU 温度、系统负载一直显示「读不到」，给了 Stellar 权限也没用。

**根因**：`File(...).readText()` 走的是本进程 untrusted_app 域，logcat 里是
`avc: denied { read } for name="loadavg" ... tcontext=u:object_r:proc_loadavg:s0`、
`name="temp" dev="sysfs"`。权限给了不等于路径通了——代码根本没经过特权通道。

**修法**：`SuccessRate.readPrivileged()` 用 `StellarShell.run(script, 6)` 把三条命令一起下发，
结果按 `SLAB=` / `LOAD=` / `TEMP=` 标签回传解析；采样策略改为「特权优先、本地兜底」，
特权通道跨进程代价高，降到 **3 秒**一次，中间用上次的值补。
温度加第三路兜底：`dumpsys thermalservice | grep -m1 -o 'mValue=[0-9.]*'`（摄氏度一位小数 ×1000），
给 sysfs 全被 SELinux 挡住的机型用；解析时**只认第一条** TEMP。

**教训**：读系统节点前先想清楚自己是什么 SELinux 域。shell 能读不代表 App 能读，
`adb shell cat` 能读也不代表 `File.readText()` 能读。

### 39. 历史页满屏「未完成 0.00s」：`append` 会凭空建记录

**根因**：`HistoryStore.append(line)` 里 `if (activeId == null && line.isNotBlank()) start(ctx, "unknown", "-", false, "")`，
任何一次 `addLog` 都会开一条 `exploit=unknown` 的记录，永远停在 `status=running`。

**修法**：`append` 改为 `val id = activeId ?: return`；
新增 `abandon(context)` 在 Controller 初始化时把残留 running 标 `interrupted`，
`stats()` 只统计 ok/failed（interrupted 不入分母）。

**教训**：写「顺带兜底」的分支前先想清楚它会在什么频率上被触发——
日志写入是每行都走的热路径，兜底等于批量生产垃圾。

### 40. 「64560 稳定链」：`title` 的 else 兜底把废案复活了

**根因**：`HistoryRecord.title` 写成 `if (exploit == "cve98260") "98260 新链" else "64560 稳定链"`，
而 64560 早已废除；历史里 `exploit` 是 `-` / `unknown` / `cve64560` 的旧记录全部显示成「64560 稳定链」。

**修法**：`title` 固定为「98260 运行链」；`exploit` 的 `optString` 缺省值从 `cve64560` 改 `cve98260`。

**教训**：`if/else` 的 else 分支不是「兜底」，是「默认值」——默认值必须跟着产品演进一起改，
否则它会把已经删掉的东西重新显示出来。

### 41. 成功率是编的：三个阈值表没有任何实测出处

**现象**：首页百分比看起来会随温度、负载变化，但用户实测发现它跟真实成败毫无关系；同一台机器同一状态下，跑成功与跑失败显示的概率一样。

**根因**：2.23.x 的 `slabFactor` / `tempFactor` / `loadFactor` 三张阈值表（340/430/540/660/900、38/43/48/56/65°C、per-core 1/2/3.5/6）是凭感觉写的，仓库与 fullchain docs 里零对应。更严重的是 `readSlab()` 读的 `posix_timers_cache` 只对 6.12 链有意义——`strings onekey-98260 | grep -c posix_timers` = **0**，6.18 引擎根本不读 slabinfo，主力机 PYB110 上权重最大的因子读的是无关计数器。

**修法**：删掉三张表，改成「实测 Beta 后验」——每次运行的真实 attempt / hit / 耗时落盘成 `run-stats.tsv`，用 Beta(1+hits, 20+misses) 给单次命中率，再按预算能跑几次折算整体成功率。环境只做 ±30% 修正，不再是主因子。

**教训**：一个会随输入变化的数字，不等于一个有依据的数字。写任何「系数」之前先问：这个系数的每个断点，是从哪次实测里读出来的？答不出来就是编的。

### 42. 引擎给了 240 秒预算，App 90 秒就判死

**现象**：真机上经常「引擎超时，已终止」，而同一台机器用 adb 手工跑引擎能成功。

**根因**：引擎 usage 含 `--budget <sec>`、内建 `--auto240`（240 秒），运行时会打印 `SLIDE=%#lx BUDGET=%llds`；而 `OneKeyEngine.kt` 的等待循环写死 `System.currentTimeMillis() + 90_000`。fullchain docs 实测「每 3~5 分钟一次命中」，90 秒只给了引擎 37% 的时间。

**修法**：`run()` 增加 `budgetMs` 参数，`SuccessRate.budgetFor(kmi)` 按内核给 300 秒（6.18）/ 180 秒（6.12）；超时文案带上累计 attempt 与命中数。

**教训**：超时值是产品决策，不是随手写的常数。它必须大于「正常路径的最坏耗时」，而这个数只能从实测分布里取。

### 43. 4 次中止把成功率天花板压到 11.5%，界面却在显示 92%

**现象**：明明每次尝试有百分之几的命中率，整体却几乎从不成功。

**根因**：`failedStageSignals >= 4` 就中止。按 docs 的 3%/attempt，4 次独立尝试的真实成功率 = 1-(1-0.03)^4 ≈ **11.5%**。这个上限从来没人算过，界面却按「三因子乘积」显示 92%。

**修法**：阈值抬到 6（→16.6%），并且把 k 直接写进成功率公式：`P = 1-(1-p)^k`，`k = min(ABORT_AFTER, budgetMs/msPerAttempt)`。界面同时显示「预计 N 次尝试」，让上限来源可见。

**教训**：概率模型必须包含所有会让过程提前结束的闸门。漏掉一个中止条件，模型给出的数字就比没有还糟——它会让人以为还有希望。

### 44. 同一开机内重复运行的成功率崩塌，环境读数完全看不出来

**现象**：第一次跑失败，再点一次几乎必然失败；重启手机后又好了。

**根因**：fullchain docs 实测：干净 cache 单步写 **15 次**命中；同一 boot 内第二次不设 `min_drain` → **0/60 ~ 0/248 全部浪费**。而 6.18 runner `strings | grep -c min_drain` = **0**，没有脏基线保护。这个变量在 slab / 温度 / 负载三个读数上完全不可见。

**修法**：新增 boot 分桶 `BootClass`（COLD_FIRST / COLD_RERUN / DIRTY），各自独立 Beta 后验；重跑桶无样本时用首次桶均值 × 0.25（`RERUN_PENALTY`）作文档化先验惩罚；重跑时 `RunConfirmDialog` 直接拦一次并建议重启。

**教训**：决定成败的变量不一定出现在仪表盘上。建模前先问「上一次运行的残留会不会影响这一次」，答案通常是会。

### 45. 写模型前先把「读数」和「依据」分开

**现象**：三物理量加权那套代码本身没有 bug，编译通过、单测也过，但结论毫无价值。

**根因**：把「能读到的量」直接当成「决定结果的量」。slab / 温度 / 负载能读到，于是被当成因子；boot 新鲜度读不到，于是被忽略——而后者才是决定性的。

**修法**：模型分两层。第一层是硬闸（二值判断，任一命中就不给数字）；第二层才是概率，且概率只来自实测样本。环境读数降级为修正系数，并锁死上下界。

**教训**：可观测不等于因果。先列「哪些变量决定结果」，再问「哪些我能量到」；两者不重合时，缺的那个必须靠分桶或硬闸补上，不能假装它不存在。
